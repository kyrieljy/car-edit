# DESIGN-20260807-002：画质参数对比测试与测试配件设置

## 元信息
- **创建日期**：2026-08-07
- **状态**：待审核
- **关联需求**：在管理后台「模型 API」菜单中，① 为每个画质参数旁添加「对比测试」按钮：首次点击时按管理员配置好的配件组合、使用对应工作流执行一次生图流程，对该参数分别取不同枚举值并行调用，结果以弹窗列表展示（第一列参数枚举值、第二列效果图、第三列「重新生成」按钮）；非首次点击直接展示上次结果。② 在该菜单最底部新增「测试配件设置」，页面效果与用户配置页左半部分一致，管理员可设置原图与每个配件位置使用的具体资源，保存后固定不变，模型 API 测试统一使用这套配置。
- **前置方案**：DESIGN-20260807-001（模型 API 画质参数可配置化，本方案在其 `ProviderImageParam` / 注入器 / 模型 API 菜单基础上扩展）

---

## 1. 背景

### 1.1 现状

DESIGN-20260807-001 已把 7 个生图 Provider 的画质参数（A 类 `quality`、B 类 `imageSize`/`resolution` 等）提炼为 Provider 级可配置项，管理员可在「系统配置 → 模型 API」的「画质参数」分区（`components/admin-console.tsx:2897` `ProviderImageParamsEditor`）逐项编辑参数名、枚举值与当前值。但目前管理员**只能盲配**：

1. **看不到效果**：把 `quality` 从 `high` 改成 `low`、把 Gemini `imageSize` 从 `512` 改成 `1K`，究竟出图差多少、值不值得，后台无任何可视反馈。要验证只能去用户端手动上传车图、手动选配件、逐个值改配置各跑一遍，成本极高。
2. **验证不成体系**：现有「一键测试所有模型」（`app/api/admin/provider-configs/test-all/route.ts` → `lib/server/provider-test.ts`）是**最小连通性测试**——`/images/edits` 分支刻意省略 `image[]`（`provider-test.ts:189-190`）、`/images/generations` 仅发 `prompt:'test'`（`:147-162`），**不产出真实改装效果图**，无法用于画质横向对比。
3. **缺少统一测试基准**：不同管理员、不同时间用不同车图和配件测试，结果不可比。

### 1.2 需求价值

给管理员一套「固定基准 + 一键横评」的画质调参闭环：先用「测试配件设置」固化一组标准输入（原图 + 配件组合 + 车漆 + 姿态），再对任一画质参数点「对比测试」，即可在同一基准下横向看到该参数各枚举值的真实出图差异，从而有依据地选定线上配置。

## 2. 功能描述

### 2.1 核心用户故事

> 作为管理员，我先在「模型 API」菜单最底部的「测试配件设置」里，像普通用户一样上传一张原车图、逐个配件位置选好具体资源、设定车漆与姿态并保存（保存后长期固定）。随后我展开某个具备「图片生成」能力的 Provider，在其「画质参数」分区看到每个参数（如 `quality`）旁多了一个「对比测试」按钮。第一次点击时，系统用我固化的这套配件组合、走该 Provider 对应的生图工作流，对 `quality` 的 `auto/low/medium/high` 四个枚举值分别并行跑一次真实生图，几十秒后弹窗以列表展示：每行「枚举值 | 效果图 | 重新生成」。之后再点该按钮直接展示上次结果；若我对某个值的图不满意，点该行「重新生成」只重跑这一个值。

### 2.2 功能点清单

| 编号 | 功能 | 说明 |
|------|------|------|
| F1 | 对比测试按钮 | 「画质参数」分区每个参数行新增「对比测试」按钮，位于该行操作区（现「删除」按钮所在的 `.provider-image-param-basic`，`admin-console.tsx:2925`）。仅 `image_generation` 能力的 Provider 显示（与画质参数分区同条件，`:2889`） |
| F2 | 首次点击并行生图 | 首次（无缓存）点击：读取全局「测试配件设置」，对**该参数下拉中的全部枚举值**（`param.options`，含形如 `__auto__`「跟随原图」的保留枚举）逐值并行执行一次生图；每次生图仅覆盖该参数为对应值，其余参数保持 Provider 当前配置 |
| F3 | 结果弹窗 | 弹窗内为单个列表：第一列「参数枚举值」（`__auto__` 显示为「跟随原图」）、第二列「效果图」（缩略图，可点击放大）、第三列「重新生成」按钮 |
| F4 | 非首次直接展示 | 非首次（已有缓存）点击：不重新生图，直接弹窗展示上次缓存结果 |
| F5 | 单值重新生成 | 弹窗每行「重新生成」仅重跑该行对应枚举值的生图，替换该行效果图；不影响其它行 |
| F6 | 纯缓存不失效 | 结果按 (Provider, 参数名, 枚举值) 持久化缓存，只要生成过就一直展示旧结果，直到管理员手动「重新生成」（本次需求确认口径） |
| F7 | 测试配件设置面板 | 「模型 API」菜单最底部新增分区，页面效果与用户配置页左半部分**一致**：原车图上传 + 按配件分类的资源选择器（含 `brand_resource`/`resource`/`resource_subcategory`/`resource_no_image` 四种 configType 分支）+ 车漆 + 姿态 |
| F8 | 全局单份配置 | 「测试配件设置」为全局单份配置（非按 Provider），保存后固定；所有 Provider 的对比测试统一取用这份配置 |
| F9 | 不扣用户额度 | 对比测试走管理员专用端点，复用完整生图工作流（提示词 / 参考图 / 质检重试），但**不消费任何用户额度、不写入 `generation_jobs` 用户生成记录** |
| F10 | 前置校验 | 未保存「测试配件设置」（缺原图或无任何配件选择）时，点「对比测试」提示先去底部配置；未落库的新建 Provider 卡片上「对比测试」按钮禁用 |

### 2.3 需求澄清结论（已与需求方确认）

| 议题 | 结论 |
|------|------|
| 对比取值范围 | **全部枚举值**：取参数下拉的 `param.options` 全集逐值对比；不额外纳入「不传（空串）」 |
| 测试配件设置范围 | **原图 + 配件 + 车漆 + 姿态**：完整复刻用户配置页左半部分全部配置项 |
| 缓存失效策略 | **纯缓存不失效**：生成过即长期展示，仅由「重新生成」刷新 |
| 生图链路 | **完整工作流、不扣用户额度**：复用 `runGenerationWorkflow` 完整管线，经管理员专用端点绕开积分扣减与用户生成记录 |

### 2.4 非功能性要求

- **成本可见**：对比测试为**真实生图**，会消耗底层模型额度/费用（一次点击 = 枚举值个数次调用，通常 4-7 次）。前端按钮与后端接口需明确这是真实调用（见风险 R2）。
- **兼容性**：不改变用户端配置模式生成的任何现有行为；画质参数配置、注入器、一键测试等既有能力保持不变。
- **数据安全**：测试配件设置与对比结果均不含敏感信息，明文存储于 SQLite。

## 3. 技术实现思路

### 3.1 整体策略

分四块落地，均建立在 DESIGN-20260807-001 既有结构之上，尽量复用、避免重写：

1. **共享配置面板（展示层复用）**：把用户配置页左半部分抽取为可复用组件，用户端与管理后台「测试配件设置」共用同一套 UI 与 configType 分支逻辑，保证「效果一致」且杜绝双份实现漂移。
2. **参数覆盖 + 短时生图（服务层）**：在生成引擎增加「强制指定生图 Provider + 覆盖单个画质参数值 + 不落用户记录/不扣额度」的短时（ephemeral）生图能力，供对比测试逐值调用。
3. **存储层**：新增两张表——全局测试配件设置、对比测试结果缓存。
4. **接口 + 后台交互（路由层 + 展示层）**：新增测试配件设置读写接口、对比测试运行/查询接口；「画质参数」分区加按钮、加结果弹窗；菜单底部加测试配件设置分区。

### 3.2 展示层：抽取共享配置面板

**问题**：用户配置页左半部分（`components/car-mod-studio.tsx:1773-2356` 的 `input-column` 子树）及其 6 个 configType 子组件（`DryCarbonPartsList:2754`、`WingStyleList:2865`、`ExhaustLayoutList:2984`、`SurfaceInstallControl:3109`、`CaliperCaseList:3241`、`PartOptionsPanel:3389`）目前**内嵌于 `car-mod-studio.tsx` 且未导出**，无法直接复用。

**方案**：抽取为受控共享组件 `components/config-panel/config-input-panel.tsx`（`ConfigInputPanel`），职责 = 渲染「原车图上传 + 配件分类手风琴 + 车漆 + 姿态」全部左半配置项，所有状态由父组件通过 props 传入并回调：

- 输入 props：`catalog`（`GET /api/catalog` 数据）、`selections`（`SelectionMap`）、`selectionOptions`（`PartSelectionOptions`）、`vehiclePreview`、`paintId`/`paintFinishEffect`/`gradientPaint`/`customPaint`/`stance` 等。
- 回调 props：`onVehicleFile`、`selectAsset`、`toggleDryCarbonPart`、`updatePartSelectionOption`、车漆/姿态 setter 等（沿用 `car-mod-studio.tsx` 现有函数语义：`selectAsset:1150`、`toggleDryCarbonPart:1192`、`onFile:1117`）。
- 类型守卫 `isBrandResourceCategory` / `isResourceNoImageCategory` / `isResourceSubcategoryCategory` / `isResourceWithImageCategory`（`car-mod-studio.tsx:449-463`）与 6 个子组件一并移入该模块。

**改造**：`car-mod-studio.tsx` 保留其全部业务状态，左半 JSX 替换为 `<ConfigInputPanel .../>`；管理后台「测试配件设置」（`AdminTestConfigPanel`）复用同一 `ConfigInputPanel`，自持一套 `selections`/`selectionOptions`/原图 state。两端像素级一致。

> 该抽取是本方案**最大改动面与最高回归点**（见风险 R1）。若评审认为整块抽取风险过高，可退化为「仅抽取 6 个 configType 子组件 + 类型守卫到共享模块，两端各自组合外层手风琴 JSX」的折中方案，代价是外层壳 JSX 少量重复。**推荐整块抽取**以保证长期一致性。

### 3.3 服务层：参数覆盖 + 短时生图

**约束（已核实）**：
- `RunGenerationWorkflowInput`（`lib/server/generation-engine.ts:9-21`）与 `GenerationProviderRequest`（`lib/server/generation-provider.ts:30-39`）当前**均无参数覆盖钩子**。
- 生图 Provider 由 `resolveNodeProvider()`（`generation-engine.ts:524-533`）+ `resolveProvider()`（`:535-537`）依「节点级 → 工作流级」解析。
- 画质参数在 `resolveImageParams(provider, vehicleImage?)`（`lib/server/provider-param-injector.ts:20-43`）内**仅读取 `provider.options.imageParams`**。
- 用户额度扣减发生在 `app/api/generations/route.ts:114` 的 `checkAndConsumeEntitlement`，**不在生成引擎内**；引擎的 `createGeneration`（`generation-engine.ts:135` → `db.ts:2510`）负责写 `generation_jobs` + `usage_ledger`。

**新增能力：`runAdminImageParamTest(input)`（`generation-engine.ts` 新增导出函数）**，复用配置模式管线但做三点差异化：

1. **强制生图 Provider**：不走工作流默认 Provider，直接以入参 `providerId` 经 `resolveProvider(providerId, catalog.providers, "image_generation")` 解析被测 Provider；解析失败或未启用则返回失败结果（不静默回退）。对比测试**关闭 fallback**（`fallbackProvider = undefined`），确保测的就是这个 Provider。
2. **覆盖单个画质参数值（Provider 浅克隆，不触库）**：构造 `patchedProvider = { ...provider, options: { ...provider.options, imageParams: imageParams.map(p => p.key === targetKey ? { ...p, value: targetValue } : p) } }`，用 `patchedProvider` 进入 `invokeGenerationProvider`。因 `resolveImageParams` 只读传入 provider 的 `imageParams`，克隆改动**仅作用于本次调用，绝不写 `provider_configs` 表**（规避 DESIGN-20260807-001 强调的 codeOwned 覆盖与 ON CONFLICT 污染问题，因为根本不落库）。当 `targetValue` 为保留值 `__auto__` 时，注入器照常走 `resolveAutoValue`（有原图，可正常自适应）。
3. **不落用户记录、不扣额度**：跳过 `checkAndConsumeEntitlement`（本就不在引擎内，管理员端点不调用即可）与 `createGeneration`；生成结果图仍经 `saveProviderImage`（`generation-provider.ts:1865`）→ `writeResultImage` 落 `data/results` + `public/results`，返回 `{ status, resultImageUrl, latencyMs, errorDetail }`。

> `runAdminImageParamTest` 与 `runGenerationWorkflow` 共享底层步骤（`getCatalog`、`getWorkflowConfigByMode("config")`、`buildConfigStandardJson`、提示词构建、`partImageUrlsForProvider:212`、`invokeGenerationWithCallPolicy`），实现时应提炼公共内部函数供两者调用，避免管线逻辑分叉。质检与重试（`evaluateGenerationResultForWorkflow`，`:85`）按需求「完整工作流」口径**保留**。

**「对应的工作流」取用**：测试配件设置为配置模式输入，故统一取 `getWorkflowConfigByMode("config")`（`db.ts:3437`，默认命中 `workflow_config_default`）作为管线骨架，再按上文强制覆盖其 `image_generation` 节点 Provider 为被测 Provider。

**原图来源**：测试配件设置保存时，原车图经上传落盘并建一条 `vehicle_uploads` 记录；对比测试以其 `vehicleUploadId` + `sourceImageUrl` 作为生图输入，图片字节经 `readLocalImageByAppUrl`（`local-images.ts:39`）回读。

### 3.4 存储层

新增两张表（见第 4 节数据库变更）：

- `admin_test_config`：全局单份测试配件设置（固定单行）。承载原图引用、车漆、姿态、`selections_json`、`selection_options_json` 等，字段对齐 `app/api/generations/route.ts` POST 所接收的配置模式输入集。
- `admin_image_param_tests`：对比结果缓存，主键唯一约束 `(provider_id, param_key, param_value)`，每行一张效果图。「首次/非首次」= 该 `(provider_id, param_key)` 下是否已有行；「重新生成」= upsert 覆盖对应 `(provider_id, param_key, param_value)` 行。按「纯缓存不失效」口径，不做基于配置变更的自动失效。

### 3.5 路由层：新增接口

1. **`GET /api/admin/test-config`**：返回全局测试配件设置（含原图 URL、车漆、姿态、selections、selectionOptions），供底部面板回显。
2. **`PUT /api/admin/test-config`**：保存全局测试配件设置。原车图沿用既有 `POST /api/admin/uploads`（`app/api/admin/uploads/route.ts`）先上传取回 URL，再随本接口 JSON 提交（或本接口直接接收 multipart，二选一，推荐前者以复用现成上传）；服务端建/更新 `vehicle_uploads` 与 `admin_test_config`。
3. **`GET /api/admin/provider-configs/compare-test?providerId=&paramKey=`**：查询该 (Provider, 参数) 的缓存结果列表（供非首次点击直接展示、及点击时判定是否首次）。
4. **`POST /api/admin/provider-configs/compare-test`**：运行对比测试。请求体 `{ providerId, paramKey, values?: string[], regenerateValue?: string }`：
   - 传 `regenerateValue` → 只跑该单值（F5「重新生成」）。
   - 否则跑 `values`（缺省 = 该参数在 Provider 配置中的 `param.options` 全集，F2）。
   - 读取全局测试配件设置 → 构建 StandardJson → 对每个值并行调用 `runAdminImageParamTest`（`Promise.allSettled`）→ upsert 至 `admin_image_param_tests` → 返回该 (Provider, 参数) 全量最新结果。
   - 缺失测试配件设置（无原图/无任何选择）或 Provider 未启用/无 `image_generation` 能力 → 返回明确错误（对应 F10）。
   - 全部端点 `requireAdminUser()` 鉴权；`runtime="nodejs"`、`dynamic="force-dynamic"`（与既有 admin 端点一致）。

### 3.6 展示层：模型 API 菜单改造

**位置与既有结构（已核实）**：`ProviderManagerV3`（`admin-console.tsx:2535-2773`）返回体中 `provider-sections`（`:2697-2769`）为最后一个可见区块，其后 `:2770` 为测试结果弹窗 portal。

1. **对比测试按钮（F1）**：在 `ProviderImageParamsEditor` 单参数行（`:2924-2958`）的 `.provider-image-param-basic`（`:2925`）内、「删除」按钮（`:2944`）旁新增「对比测试」按钮。该组件当前不持有 `provider.id`，需从 `ProviderManagerV3`（循环内 `provider.id`）→ `ProviderFields`（`:2831`）→ `ProviderImageParamsEditor`（`:2897`）逐层透传新 prop `providerId`；新建卡片（`:2686` 场景，Provider 未落库）传空并禁用按钮（F10）。
2. **结果弹窗（F3/F4/F5）**：新增 `ImageParamCompareModal`，**复刻 `ProviderTestModal`（`:2775-2829`）的 `createPortal + AnimatePresence + motion.div` 弹窗模式**（本项目无 shadcn `Dialog`），避免其双层 portal 问题（仅保留一层）。表格三列：参数枚举值（`__auto__` 用 `IMAGE_PARAM_RESERVE_LABELS` 显示「跟随原图」）、效果图缩略图、「重新生成」按钮；每行独立 loading 态。点击按钮先 `GET` 判定是否有缓存：有则直接展示，无则 `POST` 触发全量并展示 loading→结果。
3. **测试配件设置分区（F7/F8）**：在 `provider-sections` 关闭 `</div>`（`:2769`）之后、弹窗 portal（`:2770`）之前，追加 `AdminTestConfigPanel`——内部 `GET /api/catalog` 取目录、`GET /api/admin/test-config` 回显，渲染 §3.2 的 `ConfigInputPanel`，底部「保存」调 `PUT /api/admin/test-config`。
4. **样式**：沿用 `app/globals.css` 既有画质参数分区（`:6809` 起）与弹窗（`.provider-test-overlay:16397` / `.provider-test-modal:16408`）风格，遵循 ADR-0004 暗黑奢华规范补充「对比测试按钮 / 对比结果表格 / 测试配件设置分区」样式，禁止硬编码色值（用既有 CSS 变量）。

### 3.7 类型变更

- `lib/types.ts` 新增：测试配件设置类型（`AdminTestConfig`）、对比测试结果类型（`ImageParamTestResult`），并在 `AdminSummary` 中按需下发测试配件设置概要（供后台一次性加载，可选）。
- `RunGenerationWorkflowInput` 不改（新增独立的 `runAdminImageParamTest` 入参类型），或如评审倾向统一，可在其上加可选 `imageProviderIdOverride` / `imageParamOverride` / `persist` 字段——**推荐独立函数**以隔离用户生成链路，降低回归风险。

## 6. 风险与应对

| 风险 | 可能性 | 影响 | 应对措施 |
|------|--------|------|---------|
| R1：抽取 `ConfigInputPanel` 导致用户配置页回归（布局/交互错乱） | 中 | 高 | 抽取时保持 props 与现有函数语义一一对应，不改交互逻辑；抽取后逐项对照用户端四种 configType 分支手动验证 + `npm run smoke`；如风险仍高，降级为「仅抽子组件、外层各自组合」的折中方案 |
| R2：对比测试真实生图消耗底层模型额度/费用，管理员误点或频繁点开销大 | 中 | 中 | 前端按钮文案与二次确认明确「将发起 N 次真实生图」；后端并行度以 `param.options` 数为上限（通常 4-7）；单值「重新生成」精确控制；文档标注该功能有成本 |
| R3：并行多次生图 + 质检重试导致 HTTP 长耗时/超时 | 中 | 中 | 服务端 `Promise.allSettled` 汇总，单次生图沿用既有 Provider 超时；前端弹窗全程 loading，失败行单独标记可重试；必要时后续可升级为 NDJSON 逐行流式（本期不做） |
| R4：缓存永不失效，测试配件设置或参数枚举变更后旧图与新基准不一致 | 高 | 低 | 按需求方明确口径「纯缓存不失效」采纳；弹窗展示每行 `created_at` 生成时间，提示「如基准已变请重新生成」；提供整表「重新生成全部」入口 |
| R5：被测 Provider 未启用/无 `image_generation` 能力/缺 API Key | 中 | 中 | `runAdminImageParamTest` 前置校验，失败结果明确写入 `error_detail` 并在弹窗对应行展示，不静默回退 fallback |
| R6：未配置测试配件设置即点对比测试 | 中 | 低 | 后端校验原图与至少一项选择存在，缺失返回明确错误；前端提示引导至底部「测试配件设置」；新建未落库 Provider 的按钮禁用 |
| R7：`ProviderImageParamsEditor` 拿不到 `providerId` | 高 | 低 | 从 `ProviderManagerV3` 逐层透传新 prop；实施步骤单列该项，避免遗漏导致按钮无法定位 Provider |
| R8：对比测试写库/落图与用户生成混淆 | 低 | 中 | 独立表 `admin_image_param_tests` + 不调用 `createGeneration`，结果图落 `results/` 但不建 `generation_jobs`；分析模块以 `generation_jobs` 为源，天然隔离 |
