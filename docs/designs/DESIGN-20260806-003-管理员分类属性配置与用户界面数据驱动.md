# DESIGN-20260806-003：管理员分类属性配置与用户界面数据驱动

## 元信息
- **创建日期**：2026-08-06
- **状态**：已实施
- **关联需求**：管理员资源库配置界面添加分类属性（品牌-资源/资源/资源-细分类），资源类型下可配置是否有图，资源-细分类下可配置细分类选项，按"配件分类.md"重新设置所有配件的分类；约束：不影响生图 prompt 生成，不改变用户体验习惯

---

## 1. 背景

当前系统的配件分类（`asset_categories`）仅有基础属性（id/label/description/sortOrder/chatEnabled/referenceHighRisk），**没有任何字段描述分类的配置类型**。这导致两个问题：

**管理端**：管理员类型管理表单对所有分类一视同仁——品牌管理面板、品牌筛选标签、配件表单品牌字段**始终无条件渲染**，无法按分类类型差异化展示配置面板。

**用户端**：PC 端 `car-mod-studio.tsx` 和移动端 `mobile-studio-app.tsx` 通过**硬编码 categoryId 集合**（如 `brandFilteredCategoryIds = Set(["wheels","calipers"])`）决定渲染分支，与管理员配置完全脱节。新增或修改分类时需要同步修改前端代码，维护成本高且易出错。

此前曾有多份设计文档（DESIGN-20260805-002/003、DESIGN-20260806-001/002）试图解决此问题，但均**未落地到代码中**（部分文档标注"已实施"但实际代码不符）。本方案在吸收前述设计的基础上，新增"资源-细分类"的细分类选项配置能力，作为统一的完整实施方案。

---

## 2. 功能描述

### 2.1 管理员类型管理：添加分类属性

在管理员资源库配置界面的"类型管理"中，为每个分类新增**配置类型**属性，枚举值：

| 枚举值 | 显示名 | 含义 |
|--------|--------|------|
| `brand_resource` | 品牌-资源 | 需先选品牌，再选具体资源 |
| `resource` | 资源 | 直接选择具体资源 |
| `resource_subcategory` | 资源-细分类 | 选择资源后需进一步选细分类 |

选择不同配置类型后，管理端**仅显示当前类型相关的配置面板**：
- `brand_resource`：显示品牌管理面板、品牌筛选标签、配件表单品牌字段
- `resource`：隐藏品牌管理面板、品牌筛选标签、配件表单品牌字段；显示"是否显示图片"子设置
- `resource_subcategory`：隐藏品牌相关面板；显示细分类选项编辑器

### 2.2 "资源"类型：是否显示图片子设置

当配置类型为 `resource` 时，展开**"是否显示图片"**子设置（`assetImageVisible`，布尔值）：
- **显示图片**（`true`）：用户端以图片卡片展示资源（如尾翼）
- **不显示图片**（`false`）：用户端以安装开关 + 颜色材质选择展示（如前铲、侧裙）

### 2.3 "资源-细分类"类型：细分类选项配置

当配置类型为 `resource_subcategory` 时，展开**细分类选项编辑器**，允许管理员定义分组及其子选项（参考当前"排气"的 5 个布局组及子选项）。

每个细分类组包含：
- 组 ID（如 `single-side-single`）
- 组中文名（如"单边单出"）
- 组英文名（如"Single side single"）
- 排序序号
- 关联配件列表：每项包含配件 ID + 可选子标签（如"左"、"1 根"）

管理员可对细分类组进行增删改排序，对组内关联配件进行增删改。

### 2.4 按配件分类.md 重新设置分类

根据 `配件分类.md` 的分类结果，为每个现有配件设置正确的配置类型：

| 配件 | 分类 ID | configType | assetImageVisible | 说明 |
|------|---------|------------|-------------------|------|
| 轮毂 | `wheels` | `brand_resource` | — | 品牌筛选 + 资源网格 |
| 卡钳 | `calipers` | `brand_resource` | — | 品牌筛选 + 卡钳套装列表 |
| 尾翼 | `rear-wing` | `resource` | `true` | 图片卡片样式列表 |
| 前铲 | `front-bumper` | `resource` | `false` | 安装开关 + 颜色材质 |
| 侧裙 | `side-skirts` | `resource` | `false` | 安装开关 + 颜色材质 |
| 排气 | `exhaust` | `resource_subcategory` | — | 布局分组 + 子选项 |
| 机盖 | `hood` | `resource` | `true` | 干碳纤维部件成员 |
| 后视镜 | `mirrors` | `resource` | `true` | 干碳纤维部件成员 |
| 叶子板 | `fenders` | `resource` | `true` | 干碳纤维部件成员 |
| 后备箱盖 | `trunk-lid` | `resource` | `true` | 干碳纤维部件成员 |

> **干碳纤维部件**（`dry-carbon-parts`）是用户端硬编码的合成虚拟分类，不在数据库中单独存在。其 4 个成员（hood/mirrors/fenders/trunk-lid）在数据库中各自配置为 `resource` + `assetImageVisible=true`，用户端仍通过硬编码 `isDryCarbonCategory` 逻辑聚合展示，本次不改变此行为。

### 2.5 用户界面：数据驱动替代硬编码

将 PC 端和移动端的**硬编码 categoryId 集合**替换为基于 `configType` + `assetImageVisible` 的数据驱动判断，确保视觉效果与当前完全一致。

### 2.6 约束保障

- **生图 prompt 不受影响**：提示词构建引擎（`lib/generation-core.ts`、`lib/prompts.ts`）完全不读取 `configType`/`assetImageVisible`/`subcategoryConfig` 字段，仅依赖 `categoryId`/`brand`/`model`/`variant`/`colorPolicy` 等已有字段。新增字段为纯 UI 层属性，不参与提示词数据流。
- **用户体验不变**：用户端的渲染分支从硬编码改为数据驱动后，对每个分类的渲染结果必须与当前完全一致——相同的组件、相同的交互流程、相同的视觉效果。

## 3. 技术实现思路

### 3.1 数据模型扩展

**类型定义**（`lib/types.ts`）：

新增 `PartCategoryConfigType` 联合类型：`'brand_resource' | 'resource' | 'resource_subcategory'`

新增 `SubcategoryGroupAsset` 类型：包含 `assetId`（字符串）、`childLabelZh`（可选字符串）、`childLabelEn`（可选字符串）

新增 `SubcategoryGroup` 类型：包含 `id`（字符串）、`labelZh`（字符串）、`labelEn`（可选字符串）、`sortOrder`（数字）、`assets`（`SubcategoryGroupAsset[]` 数组）

扩展 `PartCategory` 类型，新增三个可选字段：`configType`（`PartCategoryConfigType`）、`assetImageVisible`（布尔）、`subcategoryConfig`（`SubcategoryGroup[]`）

**数据库**（`lib/server/db.ts`）：

`asset_categories` 表新增三列：
- `config_type TEXT NOT NULL DEFAULT 'brand_resource'`
- `asset_image_visible INTEGER NOT NULL DEFAULT 1`
- `subcategory_config_json TEXT NOT NULL DEFAULT '[]'`

迁移函数检测到列不存在时执行 `ALTER TABLE ADD COLUMN`，与现有 `reference_high_risk` 迁移模式一致。

**数据读写**：

`mapCategoryRow` 函数新增三个字段的读取：`config_type` → `configType`，`asset_image_visible` → `assetImageVisible`（布尔转换），`subcategory_config_json` → `subcategoryConfig`（JSON.parse）。

`createCategory`/`updateCategory`/`seedCategory` 函数新增三个字段的写入，`subcategoryConfig` 序列化为 JSON 字符串存储。

### 3.2 种子数据与迁移填充

**种子数据**（`lib/catalog.ts`）：

在 `v2CategorySeedBase` 的 `categoriesSeed` 派生逻辑中，新增 `defaultConfigTypeForCategory(id)`、`defaultAssetImageVisibleForCategory(id)`、`defaultSubcategoryConfigForCategory(id)` 三个函数（位于 `lib/part-category-aliases.ts`），按 2.4 节的映射表返回默认值。

排气的 `defaultSubcategoryConfigForCategory("exhaust")` 返回当前硬编码的 5 个布局组数据，结构转换为 `SubcategoryGroup[]`。

**已有数据库迁移**：

迁移函数中，对已存在的分类行按 categoryId 填充正确的 `config_type`/`asset_image_visible`/`subcategory_config_json` 值。迁移逻辑：
- `wheels`/`calipers` → `config_type='brand_resource'`
- `rear-wing`/`hood`/`mirrors`/`fenders`/`trunk-lid` → `config_type='resource'`, `asset_image_visible=1`
- `front-bumper`/`side-skirts` → `config_type='resource'`, `asset_image_visible=0`
- `exhaust` → `config_type='resource_subcategory'`, `subcategory_config_json` 填入 5 个布局组 JSON

### 3.3 API 层扩展

**管理端分类 API**（`app/api/admin/categories/route.ts` 和 `[id]/route.ts`）：

POST 和 PATCH 处理器新增解析 `configType`（字符串校验，限定三个枚举值）、`assetImageVisible`（布尔）、`subcategoryConfig`（数组结构校验）。

**目录 API**（`app/api/catalog/route.ts`）：

无需修改。`getCatalog()` 调用 `mapCategoryRow`，新增字段自动包含在返回的 `PartCategory` 对象中，前端直接可用。

### 3.4 管理端 UI 改造

**`components/admin-console.tsx`**：

**categoryForm 状态扩展**：新增 `configType`（默认 `'brand_resource'`）、`assetImageVisible`（默认 `true`）、`subcategoryConfig`（默认空数组）。

**类型管理表单**：
- 在 `referenceHighRisk` 复选框下方新增"配置类型"下拉选择框（select），选项：品牌-资源 / 资源 / 资源-细分类
- 当选择"资源"时，展开"是否显示图片"复选框
- 当选择"资源-细分类"时，展开细分类选项编辑器

**细分类选项编辑器**（新增子组件）：
- 展示当前分类下的细分类组列表，每个组为一个卡片
- 每个组卡片包含：组 ID 输入框、组中文名输入框、组英文名输入框、排序输入框
- 组卡片内展示关联配件列表：每行一个配件选择器（从当前分类的配件中选取）+ 子标签输入框 + 删除按钮
- 底部"添加分组"按钮、"添加配件"按钮
- 组卡片支持删除和拖拽排序（或上移/下移按钮）

**品牌管理面板条件渲染**：
- 计算 `selectedCategoryConfigType`：从 categoryForm 或已保存的分类数据获取
- 当 `configType !== 'brand_resource'` 时，隐藏品牌管理面板（`taxonomy-card` 品牌管理整块）
- 品牌管理面板的分类下拉框仅列出 `configType === 'brand_resource'` 的分类

**配件管理面板条件渲染**：
- 品牌筛选标签行（`brand-tags`）：仅当当前选中分类的 `configType === 'brand_resource'` 时显示
- 配件表单中的"所属品牌"字段：仅当 `configType === 'brand_resource'` 时显示在基础面板；否则隐藏

**类型列表徽章**：
- 每个分类行显示配置类型徽章（如"品牌-资源"/"资源"/"资源-细分类"）

**editCategory / saveCategory / resetCategoryForm**：同步更新以处理新增三个字段。

### 3.5 用户端 UI 数据驱动改造

**PC 端**（`components/car-mod-studio.tsx`）：

将以下硬编码常量替换为基于 `category.configType` 的动态判断：

| 原硬编码 | 替换逻辑 |
|---------|---------|
| `brandFilteredCategoryIds.has(category.id)` | `category.configType === "brand_resource"` |
| `installToggleSurfaceCategoryIds.has(category.id)` | `category.configType === "resource" && !category.assetImageVisible` |
| `category.id === "exhaust"`（渲染分支） | `category.configType === "resource_subcategory"` |
| `category.id === "rear-wing"`（渲染分支） | `category.configType === "resource" && category.assetImageVisible`（且非干碳） |
| `category.id === "calipers"`（渲染分支） | `category.configType === "brand_resource"`（且 `category.id === "calipers"`，因为轮毂走默认 asset-grid） |

**排气布局组数据源替换**：
- 删除硬编码的 `exhaustLayoutGroups` 常量
- 改为从 `category.subcategoryConfig` 读取布局组数据
- `ExhaustLayoutList` 组件接收 `subcategoryConfig` 作为 prop
- `childExhaustLayoutLabel` 函数从 `subcategoryConfig` 的 `assets[].childLabelZh/En` 读取子标签
- `exhaustLayoutLabelsById` 改为从 `subcategoryConfig` 动态生成

**`isFrontConfigAssetVisible` 函数**：
- 原逻辑基于 `fixedStyleSurfaceAssetIds` 硬编码（仅 front-bumper/side-skirts 显示固定资产）
- 替换为：当 `category.configType === "resource" && !category.assetImageVisible` 时，仅显示该分类下的第一个资产（固定资产逻辑）

**渲染分支主逻辑调整**（保持视觉效果不变）：
- `isDryCarbonCategory` 判断**保持不变**（仍硬编码 `dry-carbon-parts`，因为它是 UI 合成概念）
- `CaliperCaseList`：当 `configType === "brand_resource"` 且 `category.id === "calipers"` 时渲染
- `WingStyleList`：当 `configType === "resource" && assetImageVisible` 且非干碳时渲染
- `ExhaustLayoutList`：当 `configType === "resource_subcategory"` 时渲染
- `SurfaceInstallControl`：当 `configType === "resource" && !assetImageVisible` 时渲染
- `asset-grid`（默认）：当 `configType === "brand_resource"` 且 `category.id === "wheels"` 时渲染

**移动端**（`components/mobile/mobile-studio-app.tsx`）：

与 PC 端相同的替换策略：
- `mobileBrandFilteredCategoryIds` → `category.configType === "brand_resource"`
- `mobileInstallToggleSurfaceCategoryIds` → `category.configType === "resource" && !category.assetImageVisible`
- `mobileExhaustLayoutGroups` → 从 `category.subcategoryConfig` 读取
- `mobileExhaustLayoutLabelsById` → 从 `subcategoryConfig` 动态生成
- `MobileExhaustLayoutList` 接收 `subcategoryConfig` 作为 prop
- `mobileFixedStyleSurfaceAssetIds` → 同 PC 端 `isFrontConfigAssetVisible` 逻辑
- 渲染分支条件同步替换

### 3.6 提示词生成安全保障

`lib/generation-core.ts` 和 `lib/prompts.ts` **不做任何修改**。提示词引擎继续通过 `categoryId`/`brand`/`model`/`variant`/`colorPolicy`/`surfaceColor`/`caliperColor`/`rotorOption` 等已有字段构建提示词，不读取新增的 `configType`/`assetImageVisible`/`subcategoryConfig`。

用户选择数据流保持不变：用户选择 → `SelectionMap` → `buildConfigStandardJson()` → `GenerationPartSpec[]` → `buildGenerationPrompt()` → 提示词文本。新增字段仅影响 UI 渲染层，不进入此数据流。

## 6. 风险与应对

| 风险 | 可能性 | 影响 | 应对措施 |
|------|--------|------|---------|
| 数据驱动替换后用户端渲染结果与原硬编码不一致 | 中 | 高 | 逐分类对比替换前后的渲染组件、交互流程、视觉效果；对 7 个用户端分类逐一验收 |
| 数据库迁移失败（列已存在或数据冲突） | 低 | 中 | 迁移函数先检测列是否存在再 ALTER；迁移数据按 categoryId 精确匹配，未知分类使用默认值 |
| 排气布局组数据从硬编码迁移到数据库后格式不一致 | 中 | 中 | 严格按照现有 `exhaustLayoutGroups` 结构定义 `SubcategoryGroup` 类型；迁移数据逐字段对照 |
| 管理员修改 configType 后已有品牌/配件数据成为孤儿 | 低 | 低 | 不做强制清理，品牌和配件数据保留；非 brand_resource 类型时品牌面板隐藏但不删除数据 |
| 细分类选项编辑器交互复杂度高 | 中 | 低 | 采用卡片式分组编辑，每组独立操作；先实现基础 CRUD，排序用上移/下移按钮 |
| `subcategory_config_json` 存储大 JSON 影响性能 | 低 | 低 | 排气仅 5 组约 1KB；若未来细分类组增多可考虑独立表 |
