- **状态**：待审核

## 1. 背景

运营需求文档定义了 ModCar AI 平台运营所需的 9 大模块约 30 个子需求，建议分 7 阶段实施。当前管理后台存在三大核心缺陷：

1. **无时序聚合查询**：`/api/admin/summary` 仅返回全量计数（总数、总成本），无按日/周/月分桶的时间序列数据，无法支撑任何趋势图。
2. **无独立分页 API**：所有列表数据（生成记录、失败记录、用户列表）通过 summary API 一次性全量返回，硬编码 LIMIT 截断，无分页、无组合筛选。
3. **无图表可视化**：管理后台全部使用原生 HTML 表格展示数据，无图表库，无趋势图、饼图、柱状图。

本次方案覆盖运营需求文档建议的前 3 个阶段：
- **阶段一**：时序聚合 API 基础设施（数据层缺口 1、3、7）
- **阶段二**：生成记录分页筛选 API + 详情页 + 聚合统计卡片 + 趋势图 + 导出 + 重试（需求 2.1-2.5，数据层缺口 2）
- **阶段三**：用户活跃度/留存率查询 + 用户详情页 + 注册趋势 + 用户标签 + 用户导出（需求 1.1-1.5，数据层缺口 4、5）

技术决策：引入 Recharts 图表库；新增独立分析 API 端点（不改动现有 summary API）；延续原生 HTML + 自定义 CSS 的 UI 风格。

## 2. 功能描述

### 2.1 阶段一：时序聚合 API 基础设施

**目标**：为所有趋势图提供统一的数据查询基础。

| 功能项 | 说明 |
|--------|------|
| 通用时序聚合查询模块 | 封装按日/周/月/小时分桶的 SQL 查询函数，支持任意表、任意时间列、可选 WHERE 条件、可选分组维度 |
| 生成耗时计算 | 从 `completed_at - created_at` 计算耗时（毫秒），在查询层统一计算，无需新增数据库字段 |
| 通用 CSV 导出服务 | 封装 CSV 生成 + HTTP 响应逻辑，支持任意数据集 + 列定义，设置 `Content-Disposition` header |

### 2.2 阶段二：生成记录模块（需求 2.1-2.5）

#### 2.1 多维度筛选列表
- 独立的生成记录分页列表页，支持筛选条件任意组合：时间范围、生成模式（config/chat/全部）、任务状态（queued/running/succeeded/failed/全部）、Provider（从 provider_configs 加载）、用户（用户名/手机号模糊匹配）、配件分类（从 standard_json 解析）
- 列表展示：任务 ID、用户、模式、状态、Provider、耗时、成本、创建时间
- 支持分页（每页 20/50/100）和排序（按时间/成本/耗时）
- 顶部聚合统计卡片随筛选条件联动：总生成数、成功率、平均耗时、平均成本

#### 2.3 生成量趋势图
- 按日或小时粒度展示生成量折线图，支持切换粒度（小时/日/周）
- 可按模式（config/chat）叠加展示（多系列折线图）
- 时间范围与列表筛选联动

#### 2.4 生成详情全流程监控
- 点击单条生成记录进入详情页，展示完整生成链路
- 展示分区：基本信息卡片、标准化 JSON 折叠树、最终 Prompt 代码块、原始车辆图片预览、16 步流水线进度时间线、结果图片预览、车辆识别结果 JSON、质量检查评分卡片、错误信息警示框、成本信息卡片
- `progress_json` 解析为步骤时间线，标注每步耗时

#### 2.5 导出与快速重试
- 导出：将筛选后的生成记录列表导出为 CSV
- 快速重试：在详情页或列表行提供"重试"按钮，使用原任务输入参数重新发起生成；重试任务关联原任务 ID，详情页展示重试链路

### 2.3 阶段三：用户模块（需求 1.1-1.5）

#### 1.1 注册趋势
- 折线图展示每日/每周/每月新增用户数，支持时间范围选择（近 7 天/30 天/90 天/自定义）
- 提供同比、环比数据标注

#### 1.2 活跃度与留存
- DAU/WAU/MAU 指标折线图（活跃定义：当日有至少 1 次生成行为）
- 用户留存率：次日留存、7 日留存、30 日留存率折线图（留存定义：注册后第 N 日仍有生成行为的用户占注册用户的比例）
- 活跃用户明细列表：用户名、套餐、最近活跃时间、当日生成次数

#### 1.3 用户分类标签
- 按维度自动打标签：套餐类型（free/pro/max）、活跃度（高活/中活/低活/流失预警，基于月生成次数）、付费意愿（已付费/未付费/付费过期，关联 subscriptions.status）、用户价值（高/中/低价值，按 totalCostCents 排名分档）
- 标签支持在用户列表中作为筛选条件
- 可在用户详情页查看和手动调整标签（手动标签持久化到 users.tags_json）

#### 1.4 用户详情页
- 基本信息：用户名、手机号、套餐、角色、注册时间、最后登录时间、状态
- 额度变化时间线：额度发放、消耗、调整记录，数据来源 usage_ledger + quota_adjustments
- 生成记录列表：该用户的所有生成记录，含状态、模式、时间、成本，支持跳转到生成详情
- 偏好画像：常用车型 TOP5、常用配件分类 TOP5、常用漆色 TOP5，横向柱状图展示
- 操作日志：该用户的管理操作记录，数据来源 audit_logs（按 actor_id 或 target_id 筛选）

#### 1.5 用户导出
- 将用户列表导出为 CSV，字段包含：用户名、手机号、套餐、角色、注册时间、最后活跃时间、总生成数、总成本、标签
- 支持按当前筛选条件导出

### 3.2 时序聚合查询模块（`lib/server/analytics-queries.ts`）

封装通用时序查询函数，基于 SQLite 的 `date()` 和 `strftime()` 函数：

**核心函数设计**：
- `getTimeSeries(options)` — 通用时序查询
  - 输入：表名、时间列、起止时间、粒度（hour/day/week/month）、可选 WHERE 条件、可选分组列
  - 输出：`[{ date: string, count: number, group?: string }]`
  - 实现逻辑：根据粒度选择 SQLite 时间格式化函数（hour 用 `strftime('%Y-%m-%d %H:00', datetime(created_at/1000, 'unixepoch'))`，day 用 `date(created_at/1000, 'unixepoch')`），`GROUP BY` 格式化后的时间 + 分组列

- `getDailyActiveUsers(startDate, endDate)` — DAU 计算
  - 从 `generation_jobs` 按 `date(created_at)` + `user_id` 去重计数

- `getWeeklyActiveUsers(startDate, endDate)` / `getMonthlyActiveUsers(...)` — WAU/MAU
  - 按周/月分桶 + `DISTINCT user_id` 计数

- `getRetentionCohorts(startDate, endDate, periods)` — 留存队列
  - 按注册日分桶，对每个 cohort 检查第 N 日是否有生成行为
  - 实现逻辑：先查出每日注册用户列表（`users.created_at`），再对每个 cohort 查询 `generation_jobs` 中这些用户在第 N 日的生成记录

- `computePercentile(values, percentile)` — 百分位计算
  - 排序后取百分位位置值，用于 P50/P90/P99 计算

**时间存储说明**：项目中 `created_at` 等时间字段存储为**毫秒时间戳**（INTEGER），因此查询时需使用 `datetime(column/1000, 'unixepoch')` 转换为 SQLite 日期函数可处理的格式。

### 3.3 生成记录分页筛选 API

**`GET /api/admin/generations`**：
- 查询参数：`page`, `pageSize`, `startDate`, `endDate`, `mode`, `status`, `providerId`, `userQuery`, `partCategory`, `sortBy`（created_at/cost_credits/duration）, `sortOrder`（asc/desc）
- 响应结构：`{ items: GenerationRecord[], total: number, page: number, pageSize: number, stats: { totalCount, successRate, avgDurationMs, avgCost } }`
- stats 随筛选条件联动：在同一查询条件下计算聚合指标
- duration 在 SQL 层计算：`CASE WHEN completed_at > 0 AND created_at > 0 THEN completed_at - created_at ELSE NULL END AS duration_ms`
- partCategory 筛选：`standard_json` 中包含配件分类信息，使用 `LIKE` 模糊匹配（SQLite JSON 查询性能有限，大数据量时需评估）

**`GET /api/admin/generations/[id]`**：
- 返回完整 `generation_jobs` 记录（所有字段）
- 解析 `progress_json` 为结构化步骤数组，计算每步耗时
- 解析 `standard_json`、`vehicle_info`、`result_check_json` 为结构化对象
- 关联查询重试链路：通过 `retry_count` 和原始任务 ID 字段关联

**`POST /api/admin/generations/[id]/retry`**：
- 读取原任务的 `standard_json`、`mode`、`source_url` 等输入参数
- 调用 `generation-engine` 创建新任务，关联原任务 ID
- 写入审计日志

### 3.4 用户分析 API

**`GET /api/admin/analytics/users/registration-trend`**：
- 参数：`startDate`, `endDate`, `granularity`
- 返回：`[{ date, count }]`，并计算同比/环比（前一期同长度时间窗的计数）

**`GET /api/admin/analytics/users/activity`**：
- 参数：`startDate`, `endDate`, `granularity`
- 返回：`{ series: [{ date, dau, wau?, mau? }] }`（根据粒度返回对应指标）

**`GET /api/admin/analytics/users/retention`**：
- 参数：`startDate`, `endDate`, `periods`（逗号分隔，如 "1,7,30"）
- 返回：`[{ cohortDate, registerCount, retention: { "1": rate, "7": rate, "30": rate } }]`

**`GET /api/admin/analytics/users/active-list`**：
- 参数：`date`（默认今天）
- 返回：`[{ userId, username, plan, lastActiveAt, todayGenerations }]`

### 3.5 用户详情 API

**`GET /api/admin/users/[id]`**（新增 GET 方法，与现有 PATCH 共存）：
- 返回聚合数据对象：
  - `user`：基本信息（从 users 表 + 实时 billing 计算）
  - `tags`：自动标签（运行时计算）+ 手动标签（从 `tags_json` 读取）
  - `usageTimeline`：合并 `usage_ledger`（消耗记录）+ `quota_adjustments`（调整记录），按时间倒序，分页
  - `generations`：该用户的生成记录，分页 + 基本筛选
  - `preferences`：从 `userProfiles` 读取（已有偏好数据），或实时从 `generation_jobs.standard_json` 聚合
  - `auditLogs`：从 `audit_logs` 按 `actor_id` 或 `target_id` 筛选

**`PATCH /api/admin/users/[id]/tags`**：
- 入参：`{ tags: string[] }`（仅更新手动标签）
- 写入 `users.tags_json`，记录审计日志

### 3.6 用户标签系统

**存储方案**：`users` 表新增 `tags_json TEXT DEFAULT '[]'` 字段，存储手动标签的 JSON 数组。

**标签分类**：
- **自动标签**（运行时计算，不持久化）：根据 `users.plan`、`generation_jobs` 聚合、`subscriptions.status`、`userProfiles.totalCostCents` 实时计算
- **手动标签**（持久化到 `tags_json`）：管理员在用户详情页手动添加/删除

**自动标签判定规则**：
| 标签类别 | 判定逻辑 |
|----------|----------|
| 套餐类型 | 直接取 `users.plan` |
| 活跃度 | 查询用户最近 30 天 generation_jobs 数量：>50 高活，10-50 中活，1-10 低活，0 流失预警 |
| 付费意愿 | 查询 `subscriptions` 表是否有 status='active' 的记录 |
| 用户价值 | 查询 `userProfiles.totalCostCents`，按全部用户排名分三档（前 10% 高价值，10-40% 中价值，其余低价值） |

### 3.7 CSV 导出服务（`lib/server/export-service.ts`）

- `createCsvResponse(rows: Record[], columns: { key, label }[], filename: string): Response`
- 逻辑：将数据行按列定义拼接为 CSV 字符串，添加 BOM 头（`\uFEFF`）确保 Excel 正确识别中文，设置 `Content-Type: text/csv; charset=utf-8` 和 `Content-Disposition: attachment; filename="..."`
- 复用于：生成记录导出、用户列表导出

## 6. 风险与应对

| 风险 | 可能性 | 影响 | 应对措施 |
|------|--------|------|----------|
| SQLite 时序聚合查询性能：大数据量下 `GROUP BY date()` 可能慢 | 中 | 中 | 查询限定时间范围（最长 90 天）；现有 created_at 索引可加速；如性能不达标，考虑预聚合表 |
| standard_json 模糊匹配筛选性能：`LIKE` 查询 JSON 文本无法走索引 | 中 | 中 | partCategory 筛选为可选辅助功能，默认不启用；大数据量时考虑解析 standard_json 入独立字段 |
| 留存率计算复杂度高：需对每个注册 cohort 查询第 N 日行为 | 中 | 中 | 限制查询时间范围（最长 90 天 cohort）；批量查询替代逐用户查询 |
| Recharts 与现有 CSS 样式冲突 | 低 | 低 | 图表组件使用独立容器，样式隔离；通过 CSS 变量统一主题色 |
| 重试功能需复用生成引擎逻辑，可能涉及引擎内部 API 变更 | 中 | 高 | 重试功能在阶段二最后实现；先调研 generation-engine 的任务创建入口；如复杂度高，降级为"复制参数到生成入口"方案 |
| users 表 ALTER TABLE 在已有数据库上的兼容性 | 低 | 低 | SQLite `ALTER TABLE ADD COLUMN` 安全且不丢数据；`DEFAULT '[]'` 确保存量行有默认值 |
