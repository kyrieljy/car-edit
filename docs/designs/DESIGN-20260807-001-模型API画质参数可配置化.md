# DESIGN-20260807-001：模型 API 画质参数可配置化

## 元信息
- **创建日期**：2026-08-07
- **状态**：待审核
- **关联需求**：在管理后台「模型 API」菜单的每个模型配置中，将各生图接口的图片质量/尺寸相关参数提炼为可配置项（以 302-gpt-image2 的 `quality`（auto/low/medium/high）为例）。参数名与枚举值均可编辑，便于后续接入新接口。用户执行生成时，按此处配置调用 API。
- **需求依据文档**：`https://doc.302.ai/288853817e0`（302.AI `/v1/images/edits`）、`https://ai.google.dev/gemini-api/docs/image-generation`（Gemini 图像生成）

---

## 1. 背景

### 1.1 现状问题

项目通过可插拔多 Provider 架构（ADR-0002）接入 7 个生图 Provider。但所有影响出图画质的参数，当前**全部是代码内的硬编码常量或环境变量**，与管理后台的 Provider 配置完全无关：

| Provider | 端点类型 | 画质参数现状 | 位置 |
|----------|---------|-------------|------|
| `provider_80fce082`（302-GPT Image 2） | `/v1/images/edits` | `quality` 硬编码 `"high"` | `generation-provider.ts:1450` |
| `provider_yunwu_image_edit`（云雾 GPT Image 2） | `/v1/images/edits` | `quality` 读环境变量 `YUNWU_IMAGE_QUALITY`（默认 low） | `generation-provider.ts:1470` |
| `nano`（胜算云 Nano Banana 2） | `/images/edits` | 完全不传质量参数 | — |
| `openai`（胜算云 GPT Image 2） | `/images/generations` | 完全不传质量参数 | — |
| `provider_yunwu_nano2_edit`（云雾 Nano Banana 2，**当前默认激活**） | `:generateContent` | `imageSize` 读环境变量（默认 512） | `generation-provider.ts:1105` |
| `provider_302_nano_banana2_async_edit` | `/ws/.../nano-banana-2/edit` | `resolution` 读环境变量（默认 0.5k） | `generation-provider.ts:952` |
| 云雾 fal Nano Banana 分支 | fal 风格 JSON | `resolution` 读环境变量（默认 0.5K） | `generation-provider.ts:1099` |

由此产生三个实际痛点：

1. **调不动**：运营/管理员想提升出图清晰度，必须改代码重新部署。此前 `docs/302-image-quality-tuning.md` 已记录过一次人工排查——环境变量 `YUNWU_*` 系列对 302 端点完全不生效，容易误操作。
2. **看不见**：后台「模型 API」页面只能配 URL / 模型名 / Key / 能力，管理员无从知晓当前每个模型实际在用什么画质档位。
3. **扩不了**：每接入一个新的生图 API，都要在 `generation-provider.ts` 里新增一套参数拼装函数与环境变量读取函数。

### 1.2 协议差异这一关键约束

调研发现 7 个 Provider 分属两类互不兼容的参数协议，这是本方案所有设计取舍的根源：

- **A 类（OpenAI 兼容）**：302 / 云雾 / 胜算云的 `/images/edits` 与 `/images/generations`。原生支持 `quality`，枚举 `auto/low/medium/high`，与需求描述完全一致。同时支持 `size`、`background`、`output_format`、`output_compression`、`input_fidelity`。
- **B 类（Gemini / Nano Banana）**：`:generateContent` 与 nano-banana 系列。**Gemini 官方文档中不存在 `quality` 参数**，画质由 `imageSize`（512/1K/2K/4K）或 `resolution`（0.5k/1k/2k/4k）控制，且 Gemini 的参数嵌套在 `generationConfig.imageConfig` 之下。

若只做一个写死的 `quality` 下拉，则当前线上默认激活的生图 Provider（B 类的 `provider_yunwu_nano2_edit`）恰好用不上，需求价值落空。因此方案必须做成参数名可编辑的通用机制。

## 2. 功能描述

### 2.1 核心用户故事

> 作为管理员，我在后台「系统配置 → 模型 API」中展开任一具备「图片生成」能力的模型配置，可以看到一组「画质参数」。每个参数展示为「参数名 + 当前值下拉框」。我可以直接切换当前值（如把 302-gpt-image2 的 `quality` 从 high 改为 auto），保存后用户下一次生成即按新配置调用 API。我也可以编辑参数的可选枚举值、新增参数、删除参数，从而在不改代码的前提下适配新接入的接口。

### 2.4 两个保留语义

方案引入两个非 API 字面量的保留值，用于表达"不是一个固定取值"的语义：

| 保留值 | 存储表示 | 后台显示 | 运行时行为 |
|--------|---------|---------|-----------|
| 不传 | 空字符串 | 「不传（使用平台默认）」 | 该参数完全不出现在请求中 |
| 跟随原图 | `__auto__` | 「跟随原图」 | 调用现有自适应推导逻辑计算实际值 |

> **为何需要 `__auto__` 而非直接用 `auto`**：302 文档中 `size` 与 `background` 本身就有合法枚举值 `auto`，语义是「由平台决定」；而项目现有逻辑是「由原图宽高比决定」，两者不同。若共用 `auto` 会产生二义性，导致用户上传竖图时被强制输出横图。因此用项目保留字 `__auto__` 区分，`auto` 保持其 API 文档原义直接透传。

### 2.5 非功能性要求

- 兼容性：升级后若管理员不做任何配置改动，所有 Provider 的出图行为与升级前完全一致。
- 性能：参数解析为纯内存计算，对生成链路无可测量的额外开销。
- 数据安全：画质参数不含敏感信息，明文存储于 SQLite，不参与 API Key 的加密逻辑。

## 3. 技术实现思路

### 3.1 整体策略

采用「**数据驱动 + 内置模板兜底**」策略，分四层落地：

1. **存储层**：为 `provider_configs` 表新增通用 `options_json` 列（决策：通用 JSON 列而非专用列），承载参数定义数组。后续再增加画质以外的 Provider 级配置无需再做表迁移。
2. **模板层**：新增同构模块，按端点类型定义内置默认参数集。前端新建 Provider 时用它带出默认值，后端数据迁移时用它回填存量数据。
3. **注入层**：新增参数注入器，在生图调用前将配置解析为「实际请求参数字典」，替换现有 6 处硬编码/环境变量读取点。
4. **展示层**：在现有 `ProviderFields` 组件中新增「画质参数」分区。

### 3.2 数据结构设计

`options_json` 存储一个对象，当前仅含 `imageParams` 一个键（预留后续扩展）。`imageParams` 为参数定义数组，每个元素字段如下：

| 字段 | 类型 | 说明 |
|------|------|------|
| `key` | 字符串 | API 参数名。支持点号路径表示嵌套位置，如 `generationConfig.imageConfig.imageSize` |
| `label` | 字符串 | 后台显示名，如「图片质量」 |
| `options` | 字符串数组 | 可选枚举值列表，管理员可编辑 |
| `value` | 字符串 | 当前生效值。空串表示不传；`__auto__` 表示走自适应推导 |

对应在 `lib/types.ts` 中新增两个导出类型（参数项类型、Provider 选项类型），并在 `ProviderConfig` 上新增 `options` 字段。

### 3.3 端点类型判定与模板匹配

复用 `generation-provider.ts` 中已有的端点判定逻辑（`generationEndpoint()` 及 `is302ImageEndpoint` / `isYunwuImageEndpoint` / `isGeminiGenerateContentImageEndpoint` / `is302NanoBananaWsEditEndpoint` / `isYunwuFalNanoBananaEditEndpoint` 等谓词），将 `baseUrl` 归类到 6 个模板之一。

由于前端也需要该判定（新建 Provider 时带出模板），判定逻辑需从服务端模块中提取为**不依赖 Node 运行时的纯函数**，放置于 `lib/` 根目录以供前后端同构复用。服务端现有谓词保持不变，改为从新模块导入，避免出现两份判定标准。

### 3.4 参数注入机制

新增注入器模块，对外提供两个能力：

**能力一：解析生效参数**
输入 Provider 配置与运行时上下文（原图字节，用于自适应推导），输出扁平的「路径 → 值」字典。处理规则：
1. 跳过 `value` 为空串的参数（不传）。
2. `value` 为 `__auto__` 时，按参数名分派到现有自适应函数：`size` → `supported302ImageSize()` / `yunwuImageSize()`；`aspectRatio` 与 `aspect_ratio` → `closestNanoBananaAspectRatio()`；推导失败时回退到现有兜底值（`1024x1024` / `4:3`）。
3. 其余情况直接取字面量。
4. 依赖性校验：`output_compression` 仅在 `output_format` 生效值为 `jpeg`/`webp` 时注入（与现有 `appendYunwuImageEditOptions` 逻辑一致），否则跳过。

**能力二：写入请求体**
- 对 multipart 端点（`/images/edits`）：逐项 `formData.set()`。参数名含点号时视为非法（该类端点不支持嵌套），跳过并记录警告。
- 对 JSON 端点：按点号路径逐级创建嵌套对象后赋值。

### 3.5 调用链改造

`GenerationProviderRequest` 中已携带完整 `provider` 对象，各 `invokeXxx` 函数内部均可直接访问，因此**无需修改任何函数签名向下透传**，只需在 6 个参数拼装点改为调用注入器：

| 改造点 | 现状 | 改造后 |
|--------|------|--------|
| `append302FastImageOptions()` / `fast302ImageOptions()` | 返回硬编码常量对象 | 删除硬编码，改为调用注入器；`fast302ImageOptions()` 予以移除 |
| `appendYunwuImageEditOptions()` | 读 4 个环境变量 | 改为调用注入器 |
| `imageGenerationPayload()` 中 `fast302` 分支与 `size` 赋值 | 硬编码 + `providerOutputImageSize()` | 改为合并注入器输出 |
| `geminiImageConfigForEndpoint()` | 读环境变量 + 自适应 | 改为从注入器取嵌套路径下的值 |
| `nanoBananaWsEditPayload()` | 读环境变量 | 改为合并注入器输出 |
| `yunwuFalNanoBananaPayload()` | 读环境变量 | 改为合并注入器输出 |

同时，`providerOutputImageSize()` 由「调用链直接调用」降级为「仅被注入器在 `__auto__` 分支内部调用」；`yunwuImageEditRequestShape()`（失败日志快照）改为读取注入器的输出，保证日志与实际请求一致。

### 3.6 存量数据迁移

在 `db.ts` 的 `migrateSchema()` 中按项目既有惯例（`PRAGMA table_info` 检测 + `ALTER TABLE ADD COLUMN`）新增列，并在**首次新增该列时**为所有已存在行回填模板默认值。回填时读取环境变量的当前生效值（而非代码静态默认值），确保已在生产环境设置过 `YUNWU_IMAGE_QUALITY` 等变量的部署，升级后行为依然保持一致。

**关键约束**：`seedProviderConfigs()` 的 `ON CONFLICT DO UPDATE` 更新列清单中**不得包含** `options_json`，否则每次应用启动都会把管理员的配置重置回种子值。

### 3.7 codeOwned 覆盖陷阱的规避

`db.ts` 的 `mapProviderRow()` 对内置种子 Provider 存在「代码值覆盖数据库值」逻辑：`label` / `baseUrl` / `modelName` / `capabilities` 四个字段会被 `catalog.ts` 的种子值强行覆盖，数据库中存的值被忽略。

新增的 `options` 字段**必须采用 `consoleUrl` 的处理方式**（数据库值优先、种子值兜底），而非 `label` 那种代码优先方式。否则会出现「后台保存提示成功，但配置读不出来也不生效」的隐蔽故障——而需求点名的 `provider_80fce082` 正是内置种子 Provider。

### 3.8 前端表单数据流

现有 Provider 表单通过原生 `FormData` 提交，依赖 `name` 属性取值，不适合承载嵌套数组结构。处理方式：

- 参数列表以受控 state 维护于 `ProviderManagerV3` / `ProviderFields`。
- 在表单内放置一个隐藏字段承载序列化后的参数数组。
- `providerPayloadFromForm()` 中解析该隐藏字段，解析失败时回退到 `fallback` 值。

> 该衔接点是最易遗漏的环节：若只加了下拉框而未同步改 `providerPayloadFromForm()`，表单值会被静默丢弃。

### 3.9 校验与容错（决策：保存时校验 + 一键测试验证）

**保存时校验**（后端 API 层为准，前端做同等即时提示）：

| 校验项 | 规则 | 失败处理 |
|--------|------|---------|
| 参数名格式 | 匹配标识符及点号路径模式，段间不得为空 | 拒绝保存，返回具体错误 |
| 参数名唯一 | 同一 Provider 内不重复 | 拒绝保存 |
| 枚举列表 | 非空、去空白、去重 | 自动清洗后保存 |
| 当前值 | 必须属于枚举列表，或为空串/`__auto__` | 拒绝保存 |
| 参数条数 | 上限 20 条 | 拒绝保存 |
| 嵌套路径适用性 | multipart 端点不允许点号路径 | 拒绝保存并提示端点不支持嵌套参数 |

**一键测试验证**：扩展 `lib/server/provider-test.ts` 的 `sendMinimalTestRequest()`，使各端点的最小测试请求携带已配置的画质参数（`__auto__` 项因测试请求不含真实图片，回退到兜底值）。管理员保存后点击「一键测试所有模型」即可确认参数是否被服务端接受——若参数名或枚举值配错，302/云雾 会返回 4xx，现有分类逻辑会将其归为「参数缺失（连通性和鉴权正常）」，因此需要**细化分类逻辑**：对携带自定义参数的测试请求，若返回体中的错误信息包含参数名，判定为「参数配置错误」而非「可用」。

**运行时**：不做自动回退（避免掩盖配置错误）。Provider 返回的原始报错经现有 `providerHttpErrorMessageForUi()` 透传至生成记录与后台日志。

## 6. 风险与应对

| 风险 | 可能性 | 影响 | 应对措施 |
|------|--------|------|---------|
| `mapProviderRow()` 的 codeOwned 覆盖导致后台配置不生效 | 高 | 高 | 明确按 `consoleUrl` 的 DB 优先模式实现；在验收标准中单列一条针对内置 Provider `provider_80fce082` 的端到端验证 |
| `seedProviderConfigs()` 的 ON CONFLICT 把管理员配置重置回种子值 | 中 | 高 | 明令 `options_json` 不进入 ON CONFLICT 更新列表；验收时增加「改配置 → 重启应用 → 配置仍在」的验证 |
| 前端隐藏字段未接入 `providerPayloadFromForm()`，配置被静默丢弃 | 中 | 中 | 在实施步骤中将该改动单列为一步；验收增加「保存后刷新页面配置仍在」的验证 |
| 管理员误配参数名/枚举值，导致线上激活 Provider 生成全面失败 | 中 | 高 | 保存时强校验 + 一键测试验证；错误信息透传到生成记录；建议管理员改完立即执行一键测试 |
| `__auto__` 与 API 原生 `auto` 混淆，导致竖图被输出为横图 | 中 | 中 | 两者用不同存储值明确区分；下拉中「跟随原图」与「auto」并列展示且文案区分；在 BUSINESS_DOMAIN.md 中记录该语义 |
| 环境变量废弃后，运维仍按旧方式调参而无效 | 中 | 低 | README 明确标注废弃；应用启动时若检测到这些环境变量被设置，输出一次性警告日志指向后台配置页 |
| 一次性提炼 6 类参数，改动面较大引入回归 | 中 | 中 | 默认值严格等于现状快照，保证零行为变化；实施按「存储层 → 注入层 → UI 层」分阶段推进，每阶段可独立验证 |
| 端点判定逻辑从服务端提取为同构模块时行为漂移 | 低 | 中 | 提取时保持谓词实现原样迁移，服务端改为导入而非复制；执行 `npm run lint` 与冒烟测试 |
| `provider_302_nano_banana2_async_edit` 与 fal 分支当前禁用，缺乏真实验证环境 | 中 | 低 | 通过一键测试验证连通性；在方案中标注这两类模板为「未经生产验证」，启用时需复测 |

## 7. 实施步骤

**阶段一：类型与模板基础（可独立验证）**

1. 在 `lib/types.ts` 中定义参数项类型与 Provider 选项类型，并为 `ProviderConfig` 增加 `options` 字段。
2. 新建 `lib/provider-image-params.ts`：迁入端点类型判定纯函数、定义 6 套内置模板、定义保留值常量、实现参数清洗与校验函数。
3. 修改 `lib/server/generation-provider.ts`，将原有端点判定谓词改为从新模块导入，删除重复实现，确保现有行为不变。执行 `npm run lint` 与 `npm run smoke` 确认无回归。

**阶段二：存储层（可独立验证）**

4. 修改 `lib/server/db.ts` 建表语句，新增 `options_json` 列。
5. 在 `migrateSchema()` 中新增列检测与 `ALTER TABLE`，并实现首次迁移时按端点模板 + 环境变量生效值回填存量行。
6. 修改 `seedProviderConfigs()` 的 INSERT 列清单纳入新列，并确认 ON CONFLICT 更新列表不含该列。
7. 修改 `mapProviderRow()`，按 DB 优先、种子兜底方式映射 `options`。
8. 修改 `updateProvider()` 的入参签名、默认值兜底对象、INSERT 与 UPDATE 语句四处。
9. 修改 `lib/catalog.ts` 的 `providerSeed`，通过模板模块为 12 条记录生成 `options` 默认值。
10. 启动应用验证：数据库列已创建、存量 Provider 的 `options` 已按模板回填、重启后配置不被重置。

**阶段三：注入层（核心，可独立验证）**

11. 新建 `lib/server/provider-param-injector.ts`，实现生效参数解析（含不传跳过、`__auto__` 自适应分派、`output_compression` 依赖性判断）与两种写入方式。
12. 改造 302 multipart 分支：移除 `fast302ImageOptions()`，`append302FastImageOptions()` 改为调用注入器。
13. 改造云雾 multipart 分支：`appendYunwuImageEditOptions()` 改为调用注入器。
14. 改造 JSON 生成分支：`imageGenerationPayload()` 合并注入器输出，移除 `fast302` 布尔开关与独立的 `size` 赋值。
15. 改造 Gemini 分支：`geminiImageConfigForEndpoint()` 改为从注入器读取嵌套路径下的值。
16. 改造 nano-banana 两个分支：`nanoBananaWsEditPayload()` 与 `yunwuFalNanoBananaPayload()` 合并注入器输出。
17. 同步 `yunwuImageEditRequestShape()` 日志快照，使其读取注入器输出。
18. 清理已失效的环境变量读取函数，并在应用启动处增加一次性废弃警告日志。
19. 以 302-gpt-image2 为例做端到端验证：修改配置中的 `quality` 值，抓取实际请求确认参数随配置变化。

**阶段四：接口与后台 UI**

20. 修改 `app/api/admin/provider-configs/route.ts`，白名单新增 `imageParams` 并接入校验，校验失败返回明确错误信息。
21. 修改 `components/admin-console.tsx` 的 `ProviderFormValue`、`providerToFormValue()`、`emptyProviderForm`。
22. 修改 `providerPayloadFromForm()`，解析隐藏字段承载的参数数组（此步不可遗漏）。
23. 在 `ProviderFields` 中新增「画质参数」分区：条件渲染、参数行（参数名输入 + 当前值下拉 + 枚举编辑 + 删除）、添加参数按钮、模板重置按钮、隐藏序列化字段。
24. 实现新建 Provider 时根据填入的 API URL 自动带出内置模板。
25. 在 `app/globals.css` 中补充分区样式。

**阶段五：测试能力与文档**

26. 修改 `lib/server/provider-test.ts`，使 5 个端点的最小测试请求携带画质参数，并细化 4xx 分类以识别参数配置错误。
27. 执行 `npm run lint`、`npm run smoke`、`npm run config:validate` 全量校验。
28. 按「影响分析」表逐项更新文档：API_REFERENCE.md、DB_SCHEMA.md、CHANGELOG.md、ARCHITECTURE.md（含 ADR-0007）、BUSINESS_DOMAIN.md、README.md、docs/models.md、docs/302-image-quality-tuning.md。

- [ ] 管理后台「系统配置 → 模型 API」中，具备「图片生成」能力的 Provider 展开后显示「画质参数」分区；仅具备 llm/vision 能力的 Provider 不显示该分区。

- [ ] 重启应用后，上述配置未被种子数据重置回 `high`（验证 ON CONFLICT 未污染）。
