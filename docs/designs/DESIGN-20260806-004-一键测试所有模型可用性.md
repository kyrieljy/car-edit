# DESIGN-20260806-004：一键测试所有模型可用性

## 元信息
- **创建日期**：2026-08-06
- **状态**：已实施
- **关联需求**：在管理员界面"模型 API"页面右上角添加"一键测试所有模型"按钮，点击后并发测试所有模型 API 的可用性，弹窗以表格展示结果。测试方式为模拟真实调用但省略图片数据参数 + max_tokens=1，若接口正常返回或返回参数级错误（非连接/鉴权错误）则判定为可用。

---

## 1. 背景

管理员在"模型 API"页面配置了多个 AI 服务商的 Provider（生图、LLM、视觉识别等），但目前无法快速验证这些 Provider 的连通性和鉴权是否正常。管理员只能在生成任务失败后才发现某个 Provider 不可用，缺乏主动巡检手段。需要一个"一键测试"功能，在不实际生成内容的前提下，批量验证所有 Provider 的 API URL 可达性、API Key 有效性、模型名称可用性。

---

## 2. 功能描述

### 核心用户故事

作为管理员，我在"模型 API"页面点击"一键测试所有模型"按钮后，系统并发向所有已配置的 Provider 发送最小化测试请求，测试完成后弹窗以表格展示每个 Provider 的可用状态、耗时和详情，帮助我快速定位问题 Provider。

### 功能输入输出

- **输入**：无（自动读取数据库中所有 Provider 配置）
- **输出**：弹窗表格，包含以下列：
  - 模型备注名称（label）
  - 模型名称（modelName）
  - 能力标签（capabilities）
  - 测试状态（可用 / 不可用 / 跳过）
  - 耗时（ms）
  - 详情说明（成功/失败原因）

### 测试规则

1. **省略参数**：省略图片数据（`image` / `image_url` / `inlineData`），使请求变为纯文本或最小化请求
2. **max_tokens**：对 chat/completions 类端点设置 `max_tokens=1`（或 Gemini 的 `maxOutputTokens=1`），确保最小输出
3. **判定标准**：
   - HTTP 200 且返回有效业务数据 → **可用**
   - HTTP 400/422（参数缺失错误）→ **可用**（证明连通性和鉴权正常，仅缺少图片参数）
   - HTTP 429（限流）→ **可用**（证明连通性和鉴权正常）
   - HTTP 401/403 → **不可用**（鉴权失败）
   - HTTP 404 → **不可用**（URL 错误或模型不存在）
   - HTTP 500/502/503 → **不可用**（服务端错误）
   - 连接超时/拒绝/DNS 解析失败 → **不可用**（网络不可达）
4. **跳过条件**：
   - `id` 为 `mock` / `mock-vision` / `mock-llm` 或 `baseUrl` 以 `local://` 开头 → 跳过（本地 Mock）
   - `enabled === false` → 跳过（已停用）
   - `hasApiKey === false` → 跳过（未配置 Key）
5. **执行方式**：所有 Provider 并发测试，单次测试超时 15 秒

### 非功能性需求

- 测试请求不产生实际生成费用（对 chat 类端点仅输出 1 token；对图片编辑端点因缺少 image 参数 API 会拒绝执行）
- 对文生图端点（`/images/generations`），image 为可选参数，省略后 API 会执行文生图 — 此场景会产生极少量费用，但通过最小 prompt 和 n=1 控制
- 测试不影响现有生成流程，不修改 Provider 配置

## 3. 技术实现思路

### 整体策略

新增服务端测试模块 `lib/server/provider-test.ts`，封装按 Provider 类型分流的测试逻辑；新增 API 端点 `POST /api/admin/provider-configs/test-all` 接收管理员请求并并发执行测试；前端在 `ProviderManagerV3` 组件头部右侧添加按钮，点击后调用 API 并展示结果弹窗。

### 端点分流逻辑

根据 Provider 的 `baseUrl` 模式决定测试请求格式（复用 `generation-provider.ts` 中 `generationEndpoint` 的分流思路）：

| baseUrl 特征 | 测试请求格式 | 省略的参数 | max_tokens |
|---|---|---|---|
| 含 `/chat/completions` | JSON POST，纯文本 messages | `image_url`（消息中的图片） | `max_tokens: 1` |
| 含 `:generateContent`（Gemini） | JSON POST，纯文本 contents | `inlineData`（图片数据） | `generationConfig.maxOutputTokens: 1` |
| 含 `/images/generations` | JSON POST，最小 prompt + n=1 | `image`（参考图，可选字段） | 无（图片 API 无此参数） |
| 含 `nano-banana` | JSON POST，提交后不轮询 | `image`（图片数据） | 无（异步提交） |
| 默认（含 `/images/edits` 或其他） | FormData POST，不含 image 字段 | `image[]`（图片文件） | 无（图片 API 无此参数） |

**注意**：对于 `/chat/completions` 端点，需要处理 baseUrl 规范化 — 若 baseUrl 不以 `/chat/completions` 结尾，则自动拼接（复用 `llm-provider.ts` 中 `chatCompletionsEndpoint` 的逻辑）。

### 测试请求构造

每种端点的最小化请求体：

1. **chat/completions**：
   - URL：`{normalizedBaseUrl}`（确保以 `/chat/completions` 结尾）
   - Headers：`Content-Type: application/json`、`Authorization: Bearer {apiKey}`
   - Body：`{ model: modelName, max_tokens: 1, messages: [{ role: "user", content: "hi" }] }`

2. **Gemini generateContent**：
   - URL：`{baseUrl}`（直接使用）
   - Headers：`Content-Type: application/json`、`Authorization: Bearer {apiKey}`
   - Body：`{ contents: [{ parts: [{ text: "hi" }] }], generationConfig: { maxOutputTokens: 1 } }`

3. **images/generations**：
   - URL：`{baseUrl}`
   - Headers：`Content-Type: application/json`、`Authorization: Bearer {apiKey}`
   - Body：`{ model: modelName, prompt: "test", n: 1 }`

4. **nano-banana 异步**：
   - URL：`{baseUrl}`
   - Headers：`Content-Type: application/json`、`Authorization: Bearer {apiKey}`
   - Body：`{ model: modelName, prompt: "test" }`
   - 仅检查提交响应（不轮询结果），返回 task_id 即判定可用

5. **images/edits（FormData）**：
   - URL：`{baseUrl}`
   - Headers：`Authorization: Bearer {apiKey}`（不设 Content-Type，由 FormData 自动生成 boundary）
   - Body：FormData 包含 `model`、`prompt`、`n`、`size`，**不含 `image[]`**

### 超时控制

每个测试请求使用 `AbortController` + 15 秒超时（参照现有 `fetchWithTimeout` 模式实现）。超时后判定为"不可用"，详情为"连接超时（15s）"。

### 并发执行

使用 `Promise.allSettled()` 并发发起所有测试请求，确保单个 Provider 超时或异常不影响其他 Provider 的测试结果。

### 前端交互流程

1. 用户点击"一键测试所有模型"按钮
2. 按钮变为 loading 状态（禁用 + 显示"测试中..."文案）
3. 发起 `POST /api/admin/provider-configs/test-all` 请求
4. 等待响应（预计 3-15 秒，取决于最慢的 Provider）
5. 收到结果后，弹窗展示表格
6. 弹窗顶部显示汇总信息："共 N 个模型，X 个可用，Y 个不可用，Z 个跳过"
7. 表格按状态排序：不可用 → 可用 → 跳过，便于快速定位问题
8. 用户点击"关闭"或点击遮罩关闭弹窗

### 弹窗表格设计

| 列名 | 内容 | 宽度 |
|---|---|---|
| 模型备注名称 | Provider 的 label | 自适应 |
| 模型名称 | Provider 的 modelName | 自适应 |
| 能力 | capabilities 标签（如"生图"、"LLM"、"视觉"） | 100px |
| 状态 | 可用（绿色）/ 不可用（红色）/ 跳过（灰色） | 80px |
| 耗时 | latencyMs + "ms" | 80px |
| 详情 | 成功/失败的具体原因 | 自适应 |

## 6. 风险与应对

| 风险 | 可能性 | 影响 | 应对措施 |
|---|---|---|---|
| 文生图端点（`/images/generations`）的测试会实际生成图片，产生少量费用 | 中 | 低 | 使用最小 prompt（"test"）和 n=1 控制费用；测试频率由管理员手动触发，非自动定时 |
| 并发测试时多个 Provider 同时请求同一服务商，可能触发限流 | 低 | 低 | 15 秒超时确保不会长时间阻塞；限流响应（429）判定为"可用" |
| 异步端点（nano-banana）提交后不轮询，可能产生后台任务 | 中 | 低 | 省略 image 参数后，API 可能在异步阶段因参数缺失而失败，不会完成实际生成 |
| 部分服务商的 API 可能对异常请求返回非标准错误码 | 低 | 低 | 判定逻辑以 HTTP 状态码范围为准（2xx/4xx 非 401-403 可用，5xx/超时不可用），并在详情列展示原始状态码供管理员判断 |
| mock/local Provider 被误测试 | 低 | 无 | 显式跳过 `id` 为 mock 系列或 `baseUrl` 以 `local://` 开头的 Provider |
