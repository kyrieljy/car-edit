## 2. 功能描述

### 2.1 失败归因分析（3.2）

**核心用户故事**：运营人员希望快速了解生成失败的主要原因分布，以便针对性优化系统稳定性。

**功能输入**：
- 时间范围（days 参数，默认 30 天）
- 可选的 Provider / 模式筛选

**功能输出**：
- 饼图数据：各归因类别的失败数量及占比
- 归因类别：Provider 超时 / Provider 限流 / 内容审核拦截 / Prompt 构建失败 / 图片处理失败 / 其他
- 支持下钻：点击饼图扇区跳转到对应失败记录列表

**预期行为**：
- 基于 `generation_jobs.error_message` 字段内容进行关键词匹配分类
- 聚合计算各类别的失败数量与占比
- 与现有失败率趋势图联动（同一页面展示）

### 2.2 API 成功率监控（7.1）

**核心用户故事**：运营人员需要实时监控各 AI Provider 的稳定性，及时发现服务异常。

**功能输入**：
- 时间范围（默认近 24 小时）
- Provider 筛选（可选）

**功能输出**：
- 按小时展示各 Provider 的 API 成功率折线图
- 成功率 = succeeded 数 / 总生成数 × 100%
- 成功率低于 90% 时数据点标红告警

### 2.3 响应时间监控（7.2）

**核心用户故事**：运营人员需要了解生成服务的性能表现，识别耗时异常。

**功能输入**：
- 时间范围（默认近 24 小时）
- Provider / 模式筛选（可选）

**功能输出**：
- 按小时展示 P50 / P95 / P99 生成耗时趋势折线图
- 支持按 Provider 和模式分组对比
- 耗时计算：`completed_at - created_at`（毫秒）

### 2.4 队列积压监控（7.3）

**核心用户故事**：运营人员需要实时掌握任务队列状态，防止积压影响用户体验。

**功能输入**：无（实时查询当前状态）

**功能输出**：
- 当前 queued 状态任务数
- 当前 running 状态任务数
- 积压超过 20 任务时标红告警
- 支持前端定时轮询（每 30 秒刷新）

### 2.5 用户消息推送（8.1）

**核心用户故事**：运营人员需要向指定用户群体推送系统通知或营销活动。

**功能输入**：
- 消息标题、内容
- 目标用户筛选（全部 / 按套餐 / 按标签 / 指定用户）
- 发送方式（立即 / 定时）

**功能输出**：
- 消息写入 `account_messages` 表
- 批量发送状态反馈

### 2.6 数据报表导出（8.2 增强）

**核心用户故事**：运营人员需要定期导出运营指标报表，用于汇报和存档。

**功能输入**：
- 报表类型（日报 / 周报 / 月报）
- 时间范围
- 指标选择（用户增长 / 生成统计 / 成本汇总 / 收入汇总）

**功能输出**：
- 汇总后的 CSV / Excel 文件
- 报表包含统计周期内的关键指标聚合数据

### 2.7 生成质量评分趋势（9.1）

**核心用户故事**：运营人员需要监控 AI 生成结果的质量变化趋势。

**功能输入**：
- 时间范围（默认近 30 天）
- 粒度（日 / 周）

**功能输出**：
- 按日展示平均质量评分趋势折线图
- 标注低于阈值的日期
- 数据来源：`generation_jobs.result_check` 字段

### 2.8 Bad Case 处理效率（9.2）

**核心用户故事**：运营人员需要了解 Bad Case 的处理效率和积压情况。

**功能输入**：
- 时间范围（默认近 30 天）

**功能输出**：
- 平均处理时长（`created_at` 到 `updated_at`）
- 已处理 / 未处理数量统计
- 处理时效趋势折线图

## 3. 技术实现思路

### 3.1 整体策略

所有功能均遵循现有运营分析平台的架构模式：
1. 在 `lib/server/analytics-queries.ts` 中新增时序聚合查询函数
2. 在 `app/api/admin/analytics/` 下新增对应的 Route Handler
3. 在 `components/admin/` 下新增或扩展前端分析组件
4. 在 `admin-console.tsx` 的导航中注册新标签页

### 3.2 失败归因分析实现思路

- **归因规则引擎**：在服务端定义关键词匹配规则表（如 `{ category: "timeout", keywords: ["timeout", "超时", "time out"] }`）
- **聚合查询**：按时间范围筛选 `status='failed'` 的记录，对 `error_message` 进行规则匹配分类，统计各类别数量
- **前端展示**：在 `failure-analytics.tsx` 中新增 DonutChartCard 展示归因饼图，点击扇区调用现有生成记录筛选 API 下钻

### 3.3 系统健康监控实现思路

- **API 成功率**：复用 `getTimeSeriesSum` 基础设施，按 `provider` + `date(created_at, 'unixepoch', 'localtime', 'start of hour')` 分组，计算 `status='succeeded'` 的占比
- **响应时间**：新增 `getLatencyPercentiles` 函数，使用 SQLite 的 `NTILE` 或应用层排序计算 P50/P95/P99，按小时聚合
- **队列积压**：新增简单的状态计数查询 `getQueueStatus()`，查询 `status='queued'` 和 `status='running'` 的数量；前端使用 `setInterval` 每 30 秒轮询

### 3.4 用户消息推送实现思路

- **后端**：新增 `POST /api/admin/messages/broadcast` 接口，接收目标筛选条件和消息内容，批量写入 `account_messages` 表
- **目标用户筛选逻辑**：根据套餐/标签条件查询 `users` 表，获取目标用户 ID 列表
- **前端**：新增消息推送弹窗/页面，集成在 admin-console 的"运营工具"区域

### 3.5 数据报表导出实现思路

- 在现有 `export-service.ts` 基础上，新增报表模板逻辑
- 日报：汇总当日用户新增、生成总数、成功率、收入、成本
- 周报/月报：扩展时间跨度，增加环比数据
- 前端：新增报表生成界面，选择类型和日期后触发导出

### 3.6 内容质量分析实现思路

- **质量评分趋势**：解析 `result_check` JSON 字段中的评分值，按日聚合平均值。需先确认 `result_check` 的字段结构
- **Bad Case 处理效率**：查询 `generation_bad_cases` 表，计算 `updated_at - created_at` 的平均值，按日统计已处理/未处理数量
