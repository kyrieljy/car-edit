## 1. 背景

DESIGN-20260729-002 已完成运营分析平台的阶段一至三，建立了时序聚合基础设施（`analytics-queries.ts`）、CSV 导出服务（`export-service.ts`）、Recharts 图表组件库（`analytics-charts.tsx`），并完整实现了用户模块（模块一）和生成记录模块（模块二）的全部需求。

当前管理后台仍存在四个运营核心缺口：

1. **失败记录无趋势分析**：`getAdminSummary()` 返回 `generationFailures` 列表和 `stats.failedGenerations` 总数，但无按时间维度的失败率趋势，运营无法发现"某天失败率突然飙升"是 Provider 故障还是其他原因。
2. **Provider 成本无时序维度**：`providerCosts` 只有全量汇总（请求数、成功数、失败数、总成本），无法回答"这个月 AI 成本是否在上升""哪个 Provider 性价比最高"。
3. **订单收入无分析能力**：`GET /api/admin/orders` 仅支持列表查询，无收入趋势、转化率、续费率分析，商业化决策缺乏数据支撑。
4. **额度消耗无监控**：`usage_ledger` 记录了每次消耗，但无趋势分析、余额分布、异常告警能力，无法发现积分滥用行为。

本方案覆盖运营需求文档建议的阶段四至六，复用阶段一已建成的时序聚合基础设施，新增 12 个 API 端点、4 个前端组件、1 张数据库表。

## 2. 功能描述

### 2.1 阶段四：失败记录模块（需求 3.1-3.3）

#### 3.1 失败率趋势
- 按日/周/月展示失败率折线图，失败率 = 失败数 / 总生成数 * 100%
- 支持按生成模式（config/chat）和 Provider 分组对比
- 标注异常高峰日期（失败率超过均值 + 2 倍标准差的日期）
- 时间范围可选（近 7 天/30 天/90 天）

#### 3.2 失败归因分析（Provider 维度）
- 按 Provider 分组统计失败率排名，横向柱状图展示
- 数值为 `failureCount / requestCount * 100%`
- 支持点击下钻到该 Provider 的失败记录列表（复用已有 `GET /api/admin/generations?status=failed&providerId=xxx`）
- 附带失败原因摘要：按 Provider 聚合 `error_message` 的 TOP 5 高频关键词

#### 3.3 Provider 失败率
- 横向柱状图展示各 Provider 的失败率排名
- 与 3.2 合并为同一视图，数据来源为 `providerCosts`（已有）+ 新增时序查询

### 2.2 阶段五：Provider 成本模块（需求 4.1-4.3）

#### 4.1 成本趋势图
- 按日/周/月展示成本折线图，支持切换时间粒度
- 支持按 Provider 叠加展示（多系列折线图）
- 时间范围可选（近 7 天/30 天/90 天/自定义）
- 数据来源：`usage_ledger.created_at` + `usage_ledger.provider`

#### 4.2 成本归因
- **按用户归因**：横向柱状图展示成本 TOP10 用户，数值为 `usage_ledger` 按 user_id 聚合的 `SUM(cost_cents)`
- **按配件类型归因**：从 `generation_jobs.standard_json` 解析配件分类，JOIN `usage_ledger` 按分类聚合成本，饼图展示各配件分类成本占比

#### 4.3 单次生成成本分布
- 直方图展示单次生成的成本分布（X 轴为成本区间，Y 轴为生成次数）
- 标注 P50/P90/P99 百分位线
- 支持按 Provider 分组对比

### 2.3 阶段五扩展：订单与收入分析（需求 5.1-5.3）

#### 5.1 收入趋势
- 按日/月展示收入折线图（`payment_orders.amount_cents` 求和，仅 `status='paid'`）
- 支持按套餐（pro/max）分组对比
- 展示关键指标卡片：日收入、月收入、ARPU（每用户平均收入 = 总收入 / 付费用户数）

#### 5.2 订单转化分析
- 注册→付费转化率：付费用户数（有 `status='paid'` 订单）/ 注册用户数
- 订单状态分布饼图：pending/paid/failed/refunded 占比
- 退款率趋势：`status='refunded'` 的订单占比按日折线图

#### 5.3 订阅续费率
- 到期续费率：到期后 7 天内续费的用户占到期用户的比例
- 按月展示续费率趋势折线图
- 数据来源：`subscriptions.expires_at` + `payment_orders`（到期后有新 paid 订单视为续费）

### 2.4 阶段六：额度消耗监控（需求 6.1-6.3）

#### 6.1 额度消耗趋势
- 按日展示全平台额度消耗量折线图（`usage_ledger.usage_units` 按日求和）
- 叠加额度发放量对比（`entitlement_usage.used` 按日求和作为消耗基线 + `quota_adjustments.amount` 按日求和作为手动调整）
- 支持按套餐分组（JOIN users 表按 plan 分组）

#### 6.2 额度余额分布
- 饼图展示用户额度余额分布：已耗尽 / 即将耗尽（<20%）/ 充裕（>20%）
- 余额计算：用户当前周期额度上限（`membership_plans.credits_per_month`）- 已用额度（`entitlement_usage.used` 当前周期汇总）
- 支持点击下钻到对应用户列表

#### 6.3 异常消耗告警
- 检测规则：单用户 1 小时内生成次数 >10 或成本 >100 credits
- 新建 `alert_records` 表持久化告警记录，字段包含：用户 ID、告警类型、异常值、检测时间、状态（pending/confirmed/ignored）
- 告警列表展示：用户名、告警类型、异常时间、消耗量、状态
- 支持状态管理：确认告警、忽略告警

### 3.2 失败率趋势查询逻辑

复用 `getTimeSeries` 函数，对 `generation_jobs` 表执行两次查询：

- **总生成量时序**：`getTimeSeries({ table: "generation_jobs", timeColumn: "created_at", ... })`
- **失败量时序**：`getTimeSeries({ table: "generation_jobs", timeColumn: "created_at", whereClause: "status = 'failed'", ... })`
- 在应用层逐日合并计算失败率：`failureRate = failedCount / totalCount * 100`
- 分组场景：`groupColumn: "mode"` 或 `groupColumn: "provider_id"`
- 异常高峰标注：计算整个时间序列的均值和标准差，标注超过 `均值 + 2 * 标准差` 的日期

### 3.3 Provider 维度失败归因逻辑

从 `getAdminSummary()` 已有的 `providerCosts` 数据中提取，或新增独立查询：

- 按 Provider 分组：`SELECT provider, COUNT(*) AS total, SUM(CASE WHEN status='failed' THEN 1 ELSE 0 END) AS failed FROM generation_jobs GROUP BY provider`
- 失败率：`failed / total * 100`
- 失败原因摘要：对每个 Provider 的失败记录，提取 `error_message` 文本，按空格分词后统计词频，取 TOP 5 关键词（过滤停用词和过短词）

### 3.4 成本趋势查询逻辑

直接复用 `getTimeSeries`，数据源为 `usage_ledger` 表：

- **总成本时序**：`getTimeSeries({ table: "usage_ledger", timeColumn: "created_at", ... })`，但需要将 `COUNT(*)` 改为 `SUM(cost_cents)`
- 由于 `getTimeSeries` 固定使用 `COUNT(*)`，需扩展该函数或新增 `getTimeSeriesSum` 函数支持自定义聚合表达式
- 按 Provider 叠加：`groupColumn: "provider"`

**扩展 `analytics-queries.ts`**：新增 `getTimeSeriesSum(options)` 函数，与 `getTimeSeries` 参数相同，但聚合表达式从 `COUNT(*)` 改为 `SUM(aggregateColumn)`，支持指定 `aggregateColumn` 参数。

### 3.5 成本归因查询逻辑

- **按用户归因**：`SELECT user_id, SUM(cost_cents) AS total_cost FROM usage_ledger GROUP BY user_id ORDER BY total_cost DESC LIMIT 10`，JOIN users 表获取用户名
- **按配件类型归因**：需从 `generation_jobs.standard_json` 解析配件分类 ID，再 JOIN `usage_ledger` 按分类聚合成本。实现方式：`usage_ledger` JOIN `generation_jobs` ON `generation_id`，在应用层解析 `standard_json` 中的配件分类，按分类聚合成本

### 3.6 单次成本分布查询逻辑

- 查询 `generation_jobs.cost_credits`（或从 `usage_ledger.cost_cents` 获取），按成本值排序
- 使用 `computePercentile` 函数计算 P50/P90/P99
- 直方图分桶：在应用层将成本值分到预设区间（如 0-10/10-20/20-50/50-100/100+），统计每个区间的生成次数

### 3.7 收入趋势查询逻辑

- 数据源：`payment_orders` 表，筛选 `status = 'paid'`
- 时序查询：`getTimeSeriesSum({ table: "payment_orders", timeColumn: "created_at", whereClause: "status = 'paid'", aggregateColumn: "amount_cents", ... })`
- 按套餐分组：`groupColumn: "plan_id"`
- ARPU 计算：总收入 / 付费用户数（`SELECT COUNT(DISTINCT user_id) FROM payment_orders WHERE status = 'paid'`）

### 3.8 订单转化分析逻辑

- **注册→付费转化率**：付费用户数（有 paid 订单的用户数）/ 总注册用户数
- **订单状态分布**：`SELECT status, COUNT(*) AS count FROM payment_orders GROUP BY status`
- **退款率趋势**：`getTimeSeriesSum` 查询 `status = 'refunded'` 的订单数占 total 的比例时序

### 3.9 订阅续费率逻辑

- 查询 `subscriptions` 表中已到期的订阅（`expires_at < now`）
- 对每个到期订阅，检查到期后 7 天内是否有新的 `payment_orders` 记录（`status='paid'` 且 `created_at <= expires_at + 7天`）
- 续费率 = 有续费订单的到期用户数 / 总到期用户数
- 按月分桶计算续费率趋势

### 3.10 额度消耗趋势逻辑

- **消耗量**：`getTimeSeriesSum({ table: "usage_ledger", timeColumn: "created_at", aggregateColumn: "usage_units", ... })`
- **手动调整量**：`getTimeSeriesSum({ table: "quota_adjustments", timeColumn: "created_at", aggregateColumn: "amount", ... })`
- 按套餐分组：JOIN users 表按 plan 分组

### 3.11 额度余额分布逻辑

- 查询每个用户当前计费周期的额度上限：从 `users.plan` 获取套餐 ID，从 `membership_plans.credits_per_month` 获取月度额度
- 查询每个用户当前周期已用额度：`SELECT user_id, SUM(used) AS total_used FROM entitlement_usage WHERE date_key = <当前月份> GROUP BY user_id`
- 余额比例 = 1 - (total_used / credits_per_month)
- 分桶：已耗尽（余额 = 0）/ 即将耗尽（余额 < 20%）/ 充裕（余额 >= 20%）

### 3.12 异常消耗告警逻辑

**数据库新增 `alert_records` 表**：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | TEXT PK | 告警记录 ID |
| user_id | TEXT NOT NULL | 异常用户 ID |
| alert_type | TEXT NOT NULL | 告警类型：`high_frequency`（高频生成）/ `high_cost`（高成本消耗） |
| alert_value | INTEGER NOT NULL | 异常值（生成次数或成本值） |
| detected_at | INTEGER NOT NULL | 检测时间（毫秒时间戳） |
| status | TEXT NOT NULL DEFAULT 'pending' | 状态：pending / confirmed / ignored |
| resolved_at | INTEGER | 处理时间 |
| resolver_id | TEXT | 处理人 ID |

**检测逻辑**：新增 `lib/server/alert-scanner.ts` 模块，提供 `scanAnomalies()` 函数：
- 查询近 1 小时内每个用户的生成次数：`SELECT user_id, COUNT(*) AS count FROM generation_jobs WHERE created_at >= ? GROUP BY user_id HAVING count > 10`
- 查询近 1 小时内每个用户的成本消耗：`SELECT user_id, SUM(cost_cents) AS total FROM usage_ledger WHERE created_at >= ? GROUP BY user_id HAVING total > 100`
- 对检测到的异常，插入 `alert_records` 表（去重：同一用户同一小时同一类型不重复插入）
- 检测时机：由 API 请求触发（每次访问告警页面时执行一次扫描），不引入后台定时任务

## 6. 风险与应对

| 风险 | 可能性 | 影响 | 应对措施 |
|------|--------|------|----------|
| `standard_json` 解析配件分类性能：LIKE 查询 JSON 文本无法走索引 | 中 | 中 | 按配件分类成本归因为可选辅助功能，限定时间范围（最长 90 天）；大数据量时考虑解析 standard_json 入独立字段 |
| 续费率计算复杂度：需对每个到期订阅检查 7 天内是否有新订单 | 中 | 中 | 限制查询时间范围（最长 90 天）；使用批量 SQL 查询替代逐条查询 |
| 异常告警扫描由 API 请求触发，可能影响响应时间 | 中 | 中 | 扫描逻辑限制查询范围（近 1 小时），查询走 created_at 索引；扫描结果缓存 5 分钟（内存缓存），避免每次请求都执行扫描 |
| `alert_records` 表去重逻辑：同一用户同一小时同一类型不重复插入 | 中 | 低 | 查询时检查 `detected_at` 在当前小时窗口内是否已有同类型记录，有则跳过 |
| 成本分布直方图分桶逻辑：成本值范围可能不均匀 | 低 | 低 | 预设动态分桶策略：根据数据最小/最大值自动生成分桶区间 |
| SQLite 时序聚合性能：`GROUP BY date()` 在大数据量下可能慢 | 低 | 中 | 查询限定时间范围（最长 90 天）；现有 created_at 索引可加速 |
