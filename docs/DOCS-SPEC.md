# DOCS-SPEC.md

本文件是 Vibecoding 文档体系的元规范，定义了所有文档的格式标准、技术方案模板、以及文档更新的判断标准与操作格式。

---

## 通用约定

### 路径约定
- 本文件及所有项目文档中引用的代码路径、文件位置均使用**相对路径**（相对项目根目录）。
- 示例：`src/modules/user/controller.ts`，而非 `/home/user/project/src/...`。

### 元信息标注格式
- 每份文档末尾（或文档顶部专属区域）必须包含：
  ```
  > 最后更新时间：YYYY-MM-DD
  > 关联方案ID：DESIGN-YYYYMMDD-序号（若无关联则省略此行）
  ```

### 文档变更标记
- 新增内容以 `+` 前缀标注（仅 `doc-update` 批量更新时使用）。
- 删除内容以 `-` 前缀标注（仅 `doc-update` 批量更新时使用）。
- 修改内容在对应条目末尾标注 `(已更新 YYYY-MM-DD)`。

## 一、各文档格式规范

以下定义每份文档的**章节结构**，标记 `[必填]` 的章节不可省略，标记 `[按需]` 的章节在内容存在时才填写。

```markdown
       指向 docs/faq/ 对应文件，不在此展开。
```

### 1.2 AGENTS.md

位置：`docs/`

章节结构：

```markdown
# AI Agent 规范

[必填] ## 角色定义
       Agent 的角色、职责范围、能力边界。

[必填] ## 编码规范
       ### 命名规范
       - 变量、函数、类、常量、文件的命名规则（需可机器判定）。
       ### 代码风格
       - 缩进、引号、分号、行宽、注释格式、import/using 顺序等（需可机器判定）。
       ### 结构约定
       - 目录组织、模块划分、文件放置位置规则（需可机器判定）。
       ### 禁止事项
       - 明确禁止使用的 API、模式、写法。

[必填] ## 领域约束
       项目特定的业务规则、技术选型约束、框架使用约定。

[按需] ## UI 约束
       当项目包含前端界面时，本章节为必填。从四个层次约束 UI 产出的一致性，
       使 `code-check` 可检测、`coding` 有章可循。

       ### UI 技术栈锁定
       - **组件库**：必须使用的 UI 组件库名称及版本范围（如 `Ant Design >= 5.x`、`shadcn/ui`）。
       - **CSS 方案**：必须使用的样式方案（如 Tailwind CSS、CSS Modules、styled-components），禁止混用。
       - **图标库**：必须使用的图标库（如 `@ant-design/icons`、`lucide-react`），禁止内联 SVG 或混用多个图标库。
       - **禁止事项**：明确禁止引入的 UI 相关库（如“禁止引入 Element UI”），
         禁止的写法（如“禁止在组件中使用内联 style 覆盖组件库默认样式”）。
       > 编写提示：此小节所有条目均可被 `code-check` 通过 import 语句和 package.json 检测。

       ### 组件使用规范
       - **标准组件映射**：定义 UI 场景到组件库组件的映射关系，格式如下：
         | UI 场景 | 必须使用的组件 | 禁止的替代方式 |
         |---------|---------------|----------------|
         | 数据表格 | Table（组件库提供） | 禁止手写 HTML table |
         | 表单输入 | Form + Input/Select/DatePicker | 禁止独立使用 Input 不套 Form |
         | 操作确认 | Modal.confirm / Popconfirm | 禁止使用 window.confirm |
         | 消息提示 | message.success / notification | 禁止使用 alert |
         | 导航菜单 | Menu / Sider（组件库提供） | 禁止手写导航 |
       - **自定义组件**：若项目有自封装的通用组件（位于指定目录如 `src/components/`），
         必须在此列出组件名、用途、Props 接口，`coding` 生成 UI 时必须优先使用已有自定义组件。
       - **禁止事项**：禁止在页面中重复实现已有组件库或自定义组件能覆盖的 UI 逻辑。
       > 编写提示：此小节中“禁止事项”可被 `code-check` 通过代码模式匹配检测；
       > “标准组件映射”作为 `coding` 的组件选择依据，检测时可核对是否使用了映射表中的组件。

       ### 设计令牌（Design Tokens）
       - **令牌定义位置**：指定设计变量的文件路径（如 `src/styles/tokens.css`、`tailwind.config.js`）。
       - **必须使用的令牌类别**：
         | 类别 | 用途 | 示例 |
         |------|------|------|
         | 颜色 | 文字、背景、边框、状态色 | `--color-primary`, `--color-success` |
         | 间距 | 内边距、外边距、组件间距 | `--spacing-sm`, `--spacing-md` |
         | 圆角 | 卡片、按钮、弹窗 | `--radius-sm`, `--radius-md` |
         | 字号 | 标题、正文、辅助文字 | `--font-size-heading`, `--font-size-body` |
         | 阴影 | 卡片、弹窗、下拉菜单 | `--shadow-card`, `--shadow-dropdown` |
       - **硬编码数值禁止**：禁止在组件或页面代码中直接写死颜色值（如 `#1890ff`）、
         像素间距（如 `margin: 16px`）、字号（如 `font-size: 14px`），
         必须引用设计令牌或组件库提供的语义化变量。
         例外：`0` 和 `auto` 不受此限制。
       - **暗色/主题模式**（如有）：定义主题切换的实现方式及令牌命名规则。
       > 编写提示：此小节中“硬编码数值禁止”可被 `code-check` 通过正则匹配检测
       > （扫描颜色值 `#[0-9a-fA-F]{3,8}`、像素值 `[0-9]+px` 等模式）。

       ### 页面布局模式
       - **标准页面骨架**：定义项目中的典型页面结构，每种骨架描述其固定的区域划分。
         示例：
         ```
         列表页骨架：页面标题 + 筛选栏（可折叠）+ 数据表格 + 分页器
         详情页骨架：页面标题 + 标签页（基本信息 | 关联数据 | 操作日志）+ 底部操作栏
         表单页骨架：页面标题 + 表单分区（基本信息 / 详细配置）+ 底部提交/取消按钮
         ```
       - **布局组件**：指定项目使用的布局组件（如 `src/layouts/MainLayout.tsx`），
         所有页面必须嵌套在布局组件内，禁止脱离布局组件独立渲染页面。
       - **响应式断点**（如有）：定义项目遵循的响应式断点标准，
         与组件库或 CSS 框架的断点保持一致。
       - **禁止事项**：禁止在页面中手写与标准骨架功能重复的布局结构。
       > 编写提示：此小节主要作为 `coding` 的布局参考依据，
       > `code-check` 可检测页面是否使用了布局组件、是否包含禁止的布局模式。

[按需] ## 工具使用约定
       对特定工具或命令的使用规范。

[必填] ## 输出约束
       - 语言要求（与用户输入保持一致）。
       - 格式要求（禁止使用 emoji、输出长度限制等）。
       - 文件操作规则（如禁止擅自生成 README 等非必要文件）。

> 最后更新时间：YYYY-MM-DD
```

> **注意**：`code-check` skill 的检测能力直接取决于本文件中规范项的可判定性。编写规范时，尽量使用"必须/禁止 + 具体模式"的句式，避免模糊描述（如"代码要清晰"）。

### 1.3 CHANGELOG.md

位置：`docs/`

章节结构：

```markdown
# 变更日志

所有条目按时间倒序排列，新条目置顶。

## [版本号 或 日期标签] - YYYY-MM-DD

### 新增
- 描述 (关联方案ID: DESIGN-YYYYMMDD-序号)

### 修改
- 描述 (关联方案ID: DESIGN-YYYYMMDD-序号)

### 修复
- 描述 (关联方案ID: DESIGN-YYYYMMDD-序号，如有)

### 文档
- 描述

> 最后更新时间：YYYY-MM-DD
```

**条目格式要求**：
- 每条变更占一行，以 `- ` 开头。
- 必须注明影响范围（涉及的模块/文件/接口）。
- 有对应设计方案的，必须附带方案 ID。
- 修复类变更若无对应方案（如 `free-task` 产生），方案 ID 可省略但需注明修复原因简述。

### 1.4 BUSINESS_DOMAIN.md

位置：`docs/`

章节结构：

```markdown
# 业务领域

[必填] ## 术语表
       | 术语 | 定义 | 备注 |
       |------|------|------|
       每个业务术语一行，定义清晰无歧义。

[按需] ## 核心业务流程
       以 Mermaid 流程图为主、分步文字描述为辅，记录主要业务流程。
       每个核心流程必须同时包含流程图与分步描述，两者需一一对应。

       流程图规范：
       - 统一使用 Mermaid `flowchart` 语法，方向优先 `flowchart TD`（自上而下），
         横向流程可使用 `flowchart LR`。
       - 节点命名需与术语表中的实体名称保持一致，禁止使用与术语表冲突的别名。
       - 起点与终点必须显式标注；判断分支以菱形节点 `{}` 表示，
         并在分支连线上标注触发条件。
       - 状态转换以独立节点标注状态名称，状态值需与"业务规则"章节中的状态定义一致。
       - 涉及多角色协作的流程，使用 `subgraph` 划分泳道，每个泳道对应一个参与角色或服务。
       - 复杂流程应拆分为子流程图，主流程图通过节点链接子流程，避免单图过大。

       分步描述规范：
       - 在流程图下方以编号列表补充关键步骤说明，步骤顺序与流程图节点顺序对应。
       - 每个步骤标注参与角色、输入输出及触发的状态转换。
       - 步骤中涉及的实体与状态须与术语表一致。

[按需] ## 业务规则
       以编号列表形式记录关键业务规则，每条包含：
       - 规则编号
       - 规则描述
       - 适用条件
       - 例外情况（如有）

[按需] ## 实体关系
       描述核心业务实体之间的关系（可配合文字或图表）。

> 最后更新时间：YYYY-MM-DD
> 关联方案ID：DESIGN-YYYYMMDD-序号
```

**更新注意**：本文件涉及业务语义判断，`doc-update` 仅生成"待确认清单"，不自动覆盖。

```markdown
       - **状态**：已采纳 / 已废弃 / 已替代

       - **决策**：选择了什么方案
```

- `doc-update` 不自动修改 ADR 的"背景"和"理由"部分，仅对"状态"和"影响"字段生成待确认清单。

### 1.8 FAQ 文件

位置：`docs/faq/`

文件按领域拆分，建议文件名：`build.md`、`deploy.md`、`errors.md`、`config.md` 等，按需新增。

单文件章节结构：

```markdown
# [领域名称] 常见问题

## Q：问题描述
**现象**：用户遇到的具体表现。

**根因**：问题的技术原因。

**解决方案**：
步骤 1 ...
步骤 2 ...

**关联方案ID**：DESIGN-YYYYMMDD-序号（如该问题由某次开发引入）

---
```

**记录条件**（`free-task` 判定依据）：
- 问题由**非显而易见**的设计、配置或边缘逻辑导致时必须记录。
- 常规的语法错误、拼写错误、简单逻辑笔误无需记录。
- 同一类问题不重复记录，已有条目中追加新的解决方案变种即可。

**更新注意**：`doc-update` 不自动生成 FAQ 条目，FAQ 仅由 `free-task` 按上述条件沉淀。

### 1.9 设计方案文件

位置：`docs/designs/`

文件命名：`DESIGN-YYYYMMDD-序号-简短标题.md`
示例：`DESIGN-20260720-001-用户登录功能.md`

内容使用下方第二章的技术方案模板。

**注意**：设计方案一旦归档即只读，后续变更需新建方案并在新方案中引用原方案 ID。禁止修改已归档方案的内容。

## 二、技术方案模板

以下模板由 `requirement-analysis` skill 使用，产出存入 `docs/designs/`。

```markdown
# DESIGN-YYYYMMDD-序号：[方案标题]

## 元信息
- **创建日期**：YYYY-MM-DD
- **状态**：草稿 / 待审核 / 已通过 / 已实施 / 已废弃
- **关联需求**：用户原始需求摘要

---

## 1. 背景
描述本次需求的业务背景或问题场景。为什么需要做这件事。

## 2. 功能描述
详细描述要实现的功能或变更内容。
- 核心用户故事或用例。
- 功能的输入、输出、预期行为。
- 非功能性需求（性能、兼容性等，如有）。

## 3. 技术实现思路
描述计划如何实现，不生成代码，仅描述逻辑。
- 整体实现策略。
- 关键算法或逻辑说明。
- 与现有模块的交互方式。

## 4. 涉及的模块与文件
列出本次变更将涉及的部分：

### 代码变更
| 文件（相对路径） | 操作（新增/修改/删除） | 说明 |
|-------------------|------------------------|------|

### 数据库变更
| 表名 | 操作（新增表/新增字段/修改字段/新增索引等） | 说明 |
|------|---------------------------------------------|------|
（若无数据库变更则写"无"）

### 接口变更
| 接口路径 | 操作（新增/修改/废弃） | 说明 |
|----------|------------------------|------|
（若无接口变更则写"无"）

## 5. 影响分析
评估本次变更对系统其他部分的影响：
```

## 三、文档更新判断标准

### 3.1 更新触发条件

由 `coding` 和 `free-task` 在执行过程中判断是否需要更新文档。

| 触发条件 | 需更新的文档 | 优先级 |
|----------|-------------|--------|
| 新增、修改、废弃 API 路由或接口签名 | API_REFERENCE.md | P0 |
| 新增、修改、删除数据表或字段 | DB_SCHEMA.md | P0 |
| 任何方案执行完成 | CHANGELOG.md | P0 |
| 新增或变更架构决策（如引入新中间件、变更分层方式） | ARCHITECTURE.md（补充 ADR） | P1 |
| 变更架构概述、模块职责、部署方式 | ARCHITECTURE.md | P1 |
| 引入新的业务概念、变更业务规则、变更实体关系 | BUSINESS_DOMAIN.md | P1 |
| 变更项目启动方式、目录结构、依赖安装方式 | README.md | P2 |
| 出现值得沉淀的 FAQ 条目（由 `free-task` 判断） | docs/faq/ 对应文件 | P2 |

### 3.2 更新判定流程

`coding` skill 的判定流程：

1. 读取方案中的"影响分析"章节，提取"文档影响"表格。
2. 按表格逐文档检查：方案中标注为 P0 的，必须更新；标注为 P1 的，必须更新；标注"无"的，跳过。
3. 若实际编码过程中发现了方案未预见的影响（如临时修改了接口参数），需补充更新对应文档。
4. CHANGELOG.md 无论方案影响分析中是否标注，均必须更新。

`free-task` skill 的判定流程：

1. 修复完成后，评估修改是否影响了 API 签名或数据模型。
2. 若影响 API 签名 → 更新 API_REFERENCE.md（P0）。
3. 若影响数据模型 → 更新 DB_SCHEMA.md（P0）。
4. 若问题满足 FAQ 记录条件（见 1.8 节） → 记录到 docs/faq/。
5. CHANGELOG.md 对于 P0 级别的修复必须更新；P2 级别的微小修复可酌情省略。

### 3.3 doc-update 的增量判定

`doc-update` skill 的判定流程：

1. 基于 Git diff 获取变更文件清单。
2. 将变更文件按类型映射到文档：
   - 路由/控制器文件变更 → 对比 API_REFERENCE.md
   - Model/Schema/迁移文件变更 → 对比 DB_SCHEMA.md
   - 配置/启动文件变更 → 对比 README.md
   - 架构相关文件变更 → 对比 ARCHITECTURE.md
3. 对比方式：提取代码中的实际定义（路由路径、字段名/类型、表名等），与文档中对应条目逐条核对。
4. 分类处理：
   - **可自动更新**：API_REFERENCE.md、DB_SCHEMA.md 中可直接从代码提取的条目（路径、参数、字段定义等）→ 直接更新。
   - **需人工介入**：ARCHITECTURE.md 的 ADR 理由、BUSINESS_DOMAIN.md 的业务规则解释、FAQ 的新条目 → 生成待确认清单。

## 四、文档更新格式要求

### 4.1 条目级更新规则

- **新增条目**：在对应章节末尾追加，保持章节内排序一致（如 API 按路径字母序、DB 表按字母序）。
- **修改条目**：在原条目位置修改，不移动条目位置。修改处标注 `(已更新 YYYY-MM-DD)`。
- **废弃条目**：不直接删除，在条目顶部添加 `> **已废弃** (YYYY-MM-DD) - 原因/替代方案`，并将条目移至章节末尾的"废弃接口/表"区域（如该区域不存在则新建）。
- **删除条目**：仅在确认无任何历史引用且已废弃至少一个版本周期后，方可删除。删除时在对应文档的变更记录中注明。

### 4.2 CHANGELOG 条目格式

```
- [类型] [模块/文件] 变更描述 (关联方案ID: DESIGN-YYYYMMDD-序号)
```

类型取值：`新增`、`修改`、`修复`、`文档`、`重构`、`废弃`

示例：
```
- [新增] src/modules/auth/service.ts 实现用户登录逻辑 (关联方案ID: DESIGN-20260720-001)
- [修改] src/modules/user/controller.ts 用户查询接口新增分页参数 (关联方案ID: DESIGN-20260720-002)
- [修复] src/utils/date.ts 修复时区偏移计算错误
- [文档] docs/API_REFERENCE.md 同步用户模块接口变更 (关联方案ID: DESIGN-20260720-001)
```

### 4.3 FAQ 条目格式

```
## Q：[简明的问题描述]
**现象**：[用户遇到的具体表现]
**根因**：[技术原因]
**解决方案**：
[分步骤描述]
**关联方案ID**：DESIGN-YYYYMMDD-序号（可选）
---
```

### 4.4 ADR 条目格式

```
### ADR-NNNN：[决策标题]
- **状态**：已采纳 / 已废弃 / 已替代（由 ADR-XXXX 替代）
- **日期**：YYYY-MM-DD
- **背景**：[为什么需要这个决策]
- **决策**：[选择了什么方案]
- **理由**：[为什么选这个方案]
- **影响**：[对系统的影响范围]
- **关联方案ID**：DESIGN-YYYYMMDD-序号（如有）
```

ADR 编号从 0001 递增，不与日期绑定。
